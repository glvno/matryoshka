# Matryoshka — notes for Claude

Nord Modular–style patchable synth for the **M-VAVE FM-1**: a browser editor (`web/`, Vite + TS) with its own engine, and FM-1 firmware (`firmware/`) that plays the same patches. Owner and decider: michael glaviano (morgulbrut is the upstream Modular-1 author). Read first: `README.md`, `docs/ARCHITECTURE.md` (the design, formats, numbers), `LICENSING.md`; open work is in GitHub issues, managed on board #6 ([docs/agents/issue-tracker.md](docs/agents/issue-tracker.md), [D-069](docs/ledger/project.md#D-069)).

**`docs/ledger/`** holds every decision as a row (see "Decisions" at the end of this file). Search it before changing an area; this file only keeps what applies everywhere. Before scheduling firmware checks, read the current [validation stages](docs/EMULATOR.md#choosing-checks): use the branch roles in [D-145](docs/ledger/releases.md#D-145), candidate qualification and the reuse of checks that already passed (never re-run a passed check unless something that could change its result changed) in [D-144](docs/ledger/releases.md#D-144), and rig installation rules in [D-123](docs/ledger/releases.md#D-123).

**Emulator checks on a pull request.** A pull request runs only the checks its change touches: CI, the host tests and vitest files it changes or depends on, and `npm run emu:scenarios -- --only NAME` for each scenario it adds or changes. It never runs the full `emu:smoke` or a full `emu:scenarios` (one without `--only`). Those full suites run once, on the frozen release candidate ([D-144](docs/ledger/releases.md#D-144)). The only exceptions are installs: `emu:boot` before a build goes on the test rig ([D-123](docs/ledger/releases.md#D-123)), and `emu:smoke` before a build goes on any other FM-1 ([D-153](docs/ledger/firmware-install.md#D-153)). When a task brief asks for "the emulator gates", it means this targeted set, unless it names the full suites and says why. After every merge, CI on `main` also runs every web vitest file except the slow renders; it never gates a pull request, and a failure turns that commit's check red and opens a `main-red` issue ([D-1183](docs/ledger/releases.md#D-1183)).

## Decisions made with the user

- **No FM engine and no Felucca features.** Only Felucca's flashing path and hardware layer (HAL, USB, update loader) are reused. GPL-3.0-only for the whole repo; keep Felucca's SPDX / copyright headers on copied files.
- **Hard fork (2026-10-17):** `glvno/matryoshka` is standalone. Remotes: `origin` = glvno/matryoshka, `upstream` = WiggisModular/Modular-1 (fetch only, push URL `DISABLED`). Default branch `main`; the `deploy` workflow (`.github/workflows/pages.yml`) publishes the newest release tag (not `main`: the site pairs a released editor with its firmware; only `CHANGELOG.md` comes from `main`, and changing it there redeploys) to Cloudflare Pages (https://matryoshka.lol/, the address is `SITE_URL` in `web/src/site.ts`; https://matry0shka.pages.dev/ serves the same app); GitHub Pages (https://glvno.github.io/matryoshka/) serves only a forwarder that hands the browser data over (`deploy/github-pages-forward`, `web/src/migrate.ts`). Every change reaches `main` by pull request (since 2026-10-23); Claude may merge its own.
- Aftermarket firmwares: Felucca (`hugelton/Felucca`, GPL-3.0, reference source at `a4d7ca2e`, in `~/.jieli/felucca`; the only documentation of the hardware), Sloop (`isod89/sloop-fm1`). M-VAVE's `m-vave/fm1_open` (Apache-2.0) gave the stock V15 and the I2S rate.
- The device is a **patch player** (#57): top-level modules / assemblies are devices paged by SELECT / ALGO, K1..K4 edit the focused page (docs/ARCHITECTURE.md "Device pages").
- Factory patches are our own (`web/scripts/gen-presets.ts` from the factory assemblies), not upstream's.
- Wording: in user-visible text a stored sound is a "patch" (the PRESET knob steps patches); a "preset" is one assembly device's stored card values (#192); in the web app "voices" = polyphony. Terms: `docs/ledger/vocabulary.md`.
- The user works on macOS only. The JieLi firmware build runs in CI (`.github/workflows/firmware.yml`).

## Layout and commands

- Web (`cd web`): `npm test` (vitest), `npm run build`, `npm run dev` (the user runs one on port 5173: do not start a second). `npm run export-defs` regenerates `firmware/src/defs.h`, `factory_tier.h`, `presets.h` and the factory region image (`web/public/firmware/matryoshka-factory.bin`, `factory-sets.json`) after any change to `modules.ts`, `presets/`, or a format bump (CI checks they are committed). `npm run cpu-costs` after any engine.c change; `npm run cpu-hot` to profile. `npm run fm1-wasm` builds the firmware UI as wasm for the FM-1 tab and `engine.c` alone as wasm for the editor's FM-1 engine switch ([D-982](docs/ledger/editor.md#D-982), Decided). `npm run emu` / `emu:smoke` run the firmware in fm1-emu (docs/EMULATOR.md; choose the checks for the current stage); `emu:scenarios` drives the editor against the emulated FM-1 over a virtual MIDI port (choose targeted or full checks under [D-144](docs/ledger/releases.md#D-144); `--only NAME` reruns one); `emu:boot` is the 30 s boot check, enough only for rig installs while iterating.
- Engines: `web/src/engine.ts` + `modules.ts` (reference) ↔ `firmware/src/engine.c` (fixed point). `tools/golden.sh` compares them on every kit in `web/scripts/golden.ts`; `tools/engine_exact.sh [BASE]` proves a speed-up is bit-exact. Also `tools/panel_test.sh`, `tools/pool_sizes.sh` (stand-in pool estimate, overestimates), `tools/ui_preview.sh` (LCD to PNG).
- Generated: `python3 tools/gen_dsp_tables.py`, `gen_wavetables.py`, `gen_splash.py`, `gen_font.py`; `npx vite-node scripts/gen-assemblies.ts` then `gen-presets.ts`; `npm run logo-layers`.
- Device tools: the dev server's Flash tab installs this checkout's firmware CI build after emu:smoke passed on it (`web/dev/branch-firmware.ts`; `MATRYOSHKA_BUNDLED_FIRMWARE=1 npm run dev` for the bundled one); `npm run flash` the same from the terminal (`tools/fm1_install.py` from `build/venv`; `-- --info`, `-- x.fwsc`, `-- --ci RUN`), `tools/fm1_install.py` (preferred for flashing), `tools/m1_link.py` (editor protocol from the terminal). The test rig (the owner's second FM-1): `npm run device:scenarios` drives it; builds that passed the emulator gate may be installed on it without asking (`-- --install RUN` uses the boot check by default; `--gate full` selects the full emulator checks), never on another FM-1 (docs/EMULATOR.md, [D-123](docs/ledger/releases.md#D-123)). Patch format: `web/src/patchbin.ts` (supports through format 54 ([D-1009](docs/ledger/patch-format.md#D-1009)); patches use the oldest format that carries their features) ↔ engine.c / proto.c; protocol: `web/src/protocol.ts` ↔ `firmware/src/proto.c`.

## Rules when changing things

- Module types are appended to `ALL` in modules.ts; type / port indices are append-only. A format change: `patch.ts` (`validatePatch` migration), `patchbin.ts`, engine.c / proto.c (`ENG_PATCH_VERSION`, compat), presets, tests, golden kits, `npx vite-node scripts/legacy-factory.ts` (so the FM-1 rewrites untouched factory slots in the new format, `firmware/src/bank_upgrade.h`), `FEATURE_SYNC` in device.ts (older firmware is told to update to sync), then `export-defs` — together. A parameter appended to an existing type carries `since: <format>` (the firmware reads older records with the older count, `eng_npar`), and `tools/old_format.sh` proves older binaries still play the same (its default base is the newest release tag; at a format change also run `tools/old_format.sh v1.4.1`, format 34).
- Any change to a factory patch (an assembly, a card, a level), not only a format change: `npx vite-node scripts/legacy-factory.ts` then `npm run export-defs`, so the FM-1 gives a slot that still holds a released copy of that patch the new one when its factory set changes ([D-887](docs/ledger/patches-and-presets.md#D-887)); a preset load sets only the card's rows, so without it an update keeps the old patch. A change to a factory patch's or an example's top-level cards, or to their card sizes: first `npx vite-node scripts/factory-layout.ts <dev server>` (its header), since where Tidy puts the cards is the FM-1's page order ([D-1458](docs/ledger/device-ui.md#D-1458)).
- Which factory patches the firmware compiles in is one list, `FIRMWARE_TIER` in `web/src/factory-tiers.ts` ([D-179](docs/ledger/firmware-install.md#D-179)); every other factory patch, all factory presets and the drum patterns go to the factory region image ([D-1020](docs/ledger/patch-format.md#D-1020)). A factory patch that links factory pattern store entries (the 808 Kit, the 909 Kit) must be in the firmware tier: `export-defs` compiles their patterns in (`factory_tier.h` `KIT_GROUPS`). A change to a region patch or a preset alone can ship without a firmware release ([D-1154](docs/ledger/releases.md#D-1154), Proposed).
- Keep both engines in step: `SCALES` order, quantized increments for anything driven by an accumulator, the same idle-part rule. Add a golden kit per new module / behaviour.
- New module types need a cost in cpu-costs.json (`cpu.test.ts` fails otherwise).
- The FM-1's controls are one table, `web/src/controls.ts` ([D-913](docs/ledger/device-ui.md#D-913)): change a control's row there with its handler, then `npm run export-defs` (it writes `firmware/src/controls.h`, which the controls sheet reads); `tools/panel_test.sh` drives every row and fails when a handler no longer does what its row says. The pages' hint lines, the editor's ? card FM-1 section, `FIXED_DOES` and the README's list of controls are made from it too. Keep the rest of the ? help card and the shortcut handler in step with what the editor does. The settings menu's GUIDE (`manual.c`: ≤ 35 chars, capitals, no `;`) explains ideas, not controls: keep it in step with `docs/ledger/vocabulary.md`.

## Worktrees

These rules are in [D-074](docs/ledger/project.md#D-074) (Decided, amended).

- Work in a git worktree under `/Users/mg/projects/music/fm1/wt/<name>`, the `wt/` folder beside the main checkout `modular-1`, on a branch off `origin/main`.
- Link `web/node_modules` to the main checkout's: `ln -s /Users/mg/projects/music/fm1/modular-1/web/node_modules web/node_modules`. Never run `npm install` in a worktree. When you need the emulator, link `tools/emu/target` the same way instead of building a second one, unless your change is to the emulator itself. `m1emu` reads the factory region and the firmware headers from the checkout it runs in, so the shared build never runs another checkout's factory sounds (docs/EMULATOR.md).
- When your pull request is merged or closed, remove your worktree and its local branch: `git worktree remove <path>`, then `git branch -D <branch>`.
- After merges, run `python3 tools/worktree_gc.py --apply`. It removes every worktree whose work is kept elsewhere, and lists the rest with the reason each one stays. Without `--apply` it only prints the table. It never removes the main checkout or a path listed in the main checkout's `build/worktree-keep.txt`, such as a checkout a dev server serves. It removes uncommitted work only with `--archive`, which saves it first.
- A worktree's `build/` is deleted with the worktree. Listening files and anything else meant for the owner go to the main checkout's `build/`. `tools/engine_exact.sh` and `tools/lanes_exact.sh` delete their output when every check passes (`KEEP_EXACT=1` keeps it).

## Gotchas and lessons

- **Never flash firmware that lacks Felucca's OTA handling** (USB MIDI + `ota.c` / `ota_hw.c`): it removes the way back. Recovery = re-run the install in the loader; return to stock = bundled `web/public/firmware/FM-1_015.fwsc`. Identity: ours `FM-1_7MMmmpp` (1.8.0 = `FM-1_7010800`, dev / CI `FM-1_7000000`; 1.0..1.7 in the field `FM-1_7XY`, every parser takes both, [D-178](docs/ledger/firmware-install.md#D-178)) (loader `ota-FM-1_700`), Felucca / Sloop `FM-1_9XY`, stock `FM-1_0XX`; the `FM-1` prefix must stay.
- Fixed point: a Q16 one-pole with a small coefficient stalls short of its target; keep such states in Q24 / Q30. `exp2_q16` returns a plain integer. `sig_t` clashes with macOS `<signal.h>` (hence `esig_t`). The C name `STEPS_MAX` is a generated array.
- After a `git merge` into engine.c, read the whole file: fragments auto-merge without conflict markers.
- Never `git checkout <file>` on a file with uncommitted work.
- `pkill -f "<pattern>"` in a Bash call matches the shell itself; use `pgrep` + PID.
- Engine buffers are 128 frames; modules read `ctx.n`, not `BLOCK`. A VCA with nothing in cv is closed. An apply that deletes a module must use `removeModule`.
- Web MIDI + SysEx needs Chrome / Edge on https or localhost. Close the app's tab before CLI MIDI tools.
- fm1-emu's AArch64 JIT renders the engine wrong; `m1emu` uses the interpreter. USB, watchdog and real timing are not emulated.
