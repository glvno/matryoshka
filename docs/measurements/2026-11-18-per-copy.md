# The fixed cost per module copy, 2026-11-18

Issue #1072 (under the CPU headroom plan, #868) asks for less work per module copy before the module itself runs: the input sums, the parameter inputs (`apply_cv`), the dispatch (`render_item`) and the memory traffic. This record measures pull request #1072's cuts on the test rig and in the emulator. Every cut gives the same output samples (bit-exact, [D-356](../ledger/engine.md#D-356)).

## What changed

All in `firmware/src/engine.c`; each is the same arithmetic in the same order.

- **Parameter inputs known at load.** `eng_load` records in each module which of p1 / p2 has a cable and matrix routes (`cvp`), and which inputs have side routes (`side`). Both sit in what was padding in the module record, so the engine's RAM does not grow. `apply_cv` used to visit every input of every copy each block to find side routes; now it visits only the inputs that have some. A module with no parameter modulation copies its base values at once.
- **The block mean of a parameter input** (`signal_mean`) runs four samples a pass, out of line. A taken branch costs about 7.5 cycles on the FM-1, so the loop at one sample a pass spent more on its branch than on its sum.
- **The base values' copy** into a copy's effective values runs four values a pass.
- **No divisions per copy.** `render_item` takes the module and part numbers from its callers. Working them out from pointers cost a hardware division each (the module record is 92 bytes, the copy 264). The part's flaw factors (`apply_flaws`) are worked out only for the module types that take them, in 32 bits, where every poly copy used to pay a 64-bit division.
- **Dead branches out.** A sum always has two sources or more (`eng_load` gives an unconnected input the zero buffer, a single source its own buffer), so the sum loop's branches for none and one source are gone. A disabled input without side routes already reads the zero buffer, so only modules with a disabled input that has side routes swap their inputs each block.
- `web/src/cpu-costs.json` and the plan's table costs (`defs.h` `DEF_TCOST`) are counted again from the changed engine, as after any `engine.c` change.

## Builds and method

- **Before:** main `21b7aa25`, firmware CI run 44416627447. **After:** `fm1-percopy` `66c50cca`, firmware CI run 44434706263. Each was installed through the boot check (`emu:boot`, [D-123](../ledger/releases.md#D-123)), and the rig's dual-core check passed on each (22 of 22).
- **Load** (`tools/rig_cpu_survey.py`): each patch at 0, 1, 4 and 8 held keys, 2 seconds each, transport stopped and running. The steady value is the lower median of a phase's samples after the first. A cell is the largest steady value over the key counts, as a share of the 2,902 µs half-block.
- **Block times** (`tools/m1_link.py --rig blocktime 3 --notes 8`, with `--run` for running): means at 8 held keys. "Interrupt" is the audio interrupt; "core 0" and "core 1" are each core's busy time in it.
- **Sets:** the poly benchmark (`web/scripts/poly-bench.ts` with the owner's Hera 6 gauze 2) and the 21 factory patches of `firmware/src/presets.h`. Both builds were measured back to back in one session; `tools/m1_link.py --rig cores` before and after each: 2 cores, no bar, no failed self-test, no refused job.
- **Bit-exact:** `tools/engine_exact.sh origin/main` (also with `EXACT_CFLAGS=-DENG_AOT=1`) and `tools/lanes_exact.sh origin/main`: all 547 kits, the transition checks and the 21 factory patches identical, in every mode of the second core, and no race under ThreadSanitizer.
- **Memory** (CI build log, the same as main): pool headroom 8,200 B, `.lowram` 48 B free, RAM 4,476 B free, NOINIT 156 B free after the RAM code. Image 555,916 B (main 556,492 B).
- **Raw data:** [per-copy-2026-11-18-rig.json](per-copy-2026-11-18-rig.json).

## Tried and left out

- **Sums with their pointers stepped on** instead of indexed (CI run 44433472471): no quicker in the timing model (`render_item` +3,800 cycles a half). The indexed loops stay.
- **`signal_mean` in the RAM code:** it is 186 bytes and NOINIT has 156 left; it refills about one cache line a half, so the RAM would save under 1,000 cycles a half.
- **Skipping unconnected inputs' sums:** nothing to skip. An unconnected input reads the zero buffer and a single source is read in place, both since `eng_load`; only inputs with two or more sources are summed, and that is the copy's real work.
- **A function table in place of `process`'s switch:** the switch is one jump table. What every copy pays there is the function's entry, which loads about eight addresses and saves twelve registers for the biggest module. Splitting the 48 KB function so each module had its own entry would change the code layout, to which the FM-1 is sensitive; not tried.
- **Skipping the base values' copy when nothing changed:** many places write a module's parameters (the knobs, ramps, P-locks, morph, preset loads), so a skipped copy would need a change count kept by all of them. The copy now runs four values a pass instead.
- **Batching tiny modules, a compact state layout:** the modules' state is in RAM, which has no cache on the FM-1, so a smaller layout saves no fetches; batching would need the plan and both render paths to change, for a part of the cost the steps above already cut.
