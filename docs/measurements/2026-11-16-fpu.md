# The AC791N's FPU on the test rig, 2026-11-16

Issue #950: our firmware was built without the FPU flags, so the benchmark behind [D-352](../ledger/engine.md#D-352) (the audio path is fixed point only) measured software float, not the chip. This record measures the chip's single-precision FPU (floating-point unit) with our toolchain, beside the engine's fixed-point kernels doing the same jobs.

- **Builds:** firmware CI run 43928668815 (pull request #974, branch `docs_fpu-measure` on main `23e156c5`), artifact `matryoshka-fpu-measure`: `bench-soft` (`M1_BENCH=1`, software float) and `bench-fpu` (`M1_BENCH=1 FM1_FPU=1`). Both passed `npm run emu:boot` before going on the rig.
- **Run:** on the test rig, each build installed with `tools/fm1_install.py PACKAGE --rig --yes --no-factory`, then `tools/m1_link.py --rig fpubench --json FILE` twice. The CPU clock from the same page's timed adds: 359.9 MHz.
- **Files:** `fpubench-2026-11-16-rig-soft-1.json`, `-soft-2.json`, `-fpu-1.json`, `-fpu-2.json`. The two runs of each build agree within 1 % on every kernel; the tables use the first.
- **Method** (`firmware/src/bench.c`): each kernel processes one 128-frame block with the interrupts off, 8 times; the fastest run counts (warm caches). "Per op" is the time less the block loop's (the first kernel), divided by the operations the kernel chains a sample; each operation waits for the one before, so it is the latency. Every kernel's result bits are reported.

## Result bits

Both builds give the same result bits on every kernel. Every kernel except the libm ones also matches a host build with IEEE single precision (Apple clang, `-ffp-contract=off`), and so do `sinf`, `cosf`, `expf` and `exp2f`; `log2f` differs from the Mac's libm (newlib computes it as `logf(x) / ln 2`). So the FPU rounds as IEEE single precision does, with gradual underflow, and the hardware libm returns what the software libm returns.

- **Float operations on the FPU:** an add or a multiply costs 1.6 cycles in a dependent chain, a divide or a multiply then an add 3.0, a conversion between int and float 2.3. In software float they cost 112 to 268 cycles, so the old benchmark's 40 to 70 times was software float.
- **Subnormal numbers cost nothing extra on the FPU:** a chain on subnormal operands takes the same 1.6 cycles an operation, and the six resonator modes ringing in the subnormal range take 205.6 cycles a sample against 206.6 with a normal signal. The ±1e-15 offset that keeps a decaying filter out of that range (OpenPocket's) is not needed for speed. No flush-to-zero mode is known for this FPU, and none was needed.
- **libm on the FPU:** `sinf` 241, `cosf` 239, `expf` 187, `log2f` 208 cycles a call (less the loop). `exp2f` goes through `powf` (478). A float `2^x` written as a degree-5 polynomial costs 38 cycles; the engine's `exp2_scale` costs 85.
- **The engine's kernels against float:**
  - Two biquad sections (`dly_aa`): 88.8 fixed, 67.7 float.
  - Six resonator modes as `m_modal` runs them now (rotated state pairs with a step toward zero, #840): 441.6 fixed, 206.6 float (2.1 times faster). The older two-pole form: 297.2 fixed, 117.0 float.
  - One-pole: 22.4 fixed, 18.4 float. State variable filter: 23.4 to 24.4 fixed, 21.4 float.
  - Oscillator (parabolic sine): 17.3 fixed (Q15), 28.5 float. Four multiply-adds: 27.3 both. Float to a 16-bit output: 12.4.
  - The engine's Q multiply (32 x 32 -> 64 bits, shifted) costs 9.3 cycles in a chain; a float multiply 1.6.

Float wins where the fixed-point code needs 64-bit products, rounding care or wide states (filters, resonators); it loses on phase accumulators, where integers wrap for free.

## The build

- **Flags.** `FM1_FPU=1` adds `-mcpu=r3 -mfprev1 -ffp-contract=off` to the app's compile, what JieLi's AC79 SDK (`apps/*/board/wl82/Makefile`) and FM1 Open (`sdk/Build.ps1`) use, and links the toolchain's `pi32v2/lib/r3/` libraries instead of `pi32v2/lib/`. The default libraries are the `r1` build (`lib/libm.a` is byte for byte `lib/r1/libm.a`), whose float helpers and libm are software float. In `lib/r3/` the libm members use the FPU and call no helper.
- **Float calling convention.** Nothing had to change. A float travels in the integer registers `r0` to `r3` with or without the FPU (the FPU works on the integer registers), and every object file in both library sets has ELF flags 0.
- **What links.** The FPU benchmark build calls no software float helper (`tools/fpu_compare.py`: 0 calls, 705 FPU instructions); the software float build calls them 795 times. libm's `sinf`, `cosf`, `expf`, `log2f` and `exp2f` need only libm itself (newlib's IEEE wrappers: no `errno`, no libc). The benchmark keeps its buffers in NOINIT and adds no `.data` or `.bss`.
- **The normal firmware with the FPU flags is the same firmware.** `FM1_FPU=1` without the benchmark builds an app byte for byte equal to the normal build (sha256 `55d8d9de…`, main's CI build of `23e156c5`). The firmware has no float, and `-mcpu=r3` changes no integer code.
- **JieLi's objdump cannot print the FPU's instructions.** It shows each as `<unknown instruction>` and can read its second half as another instruction. `tools/build.py`'s checks of the disassembly (no call into the chip ROM, no call or flash address in `.ram_text` and `.c1_text`) do not see them. That is harmless while no float code runs from RAM; float in `.ram_text` or `.c1_text` would need those checks to know the FPU's encodings (fm1-emu's `fm1-isa/src/fpu.rs` lists them).
- **Emulator.** fm1-emu (pinned `7ca5b96`) decodes the FPU's instructions and executes them with the host's single-precision float. `npm run emu:boot` passes (32 checks each) on the `FM1_FPU=1` build and on both benchmark builds of run 43928668815. Its timing does not model the FPU.

## The 64-bit multiply erratum (reported, not fixed)

felucca-bsp's `docs/CPU.md` reports that on the FM-1 at 360 MHz an inlined 32 x 32 -> 64-bit multiply among 16-bit loads now and then leaves a register one bit off; floating-point code never showed it. `tools/fpu_compare.py` lists the normal build's functions with inlined 64-bit multiplies and 16-bit loads:

- 40 functions hold 1,851 64-bit multiplies. The engine's multiply helpers are always inlined, so nearly all of them are on the audio path.
- 18 of those functions also load 16-bit values: the delay lines and the reverb (`dly_tape` 90 multiplies and 40 16-bit loads, `reverb_kernel` 43 and 26, `dly_slow` 32 and 16, `dly_glide` 15 and 4), `process` (683 and 42), `eng_render`, `render_item`, the audio interrupt `fm1_alnk0_irq`, and some control code.
- 5 have a multiply within 3 instructions of a 16-bit load: `ana_init` (4), `process` (3), `dly_tape`, `reverb_kernel` and `dly_glide` (1 each).

So the engine has the pattern the erratum describes. No crash or one-bit error on our firmware has been traced to it, and whether it strikes our code is not known. A float audio path would replace most of these multiplies; 16-bit delay lines would keep their loads.

## Options for D-352

[D-352](../ledger/engine.md#D-352) rests on the first benchmark, which measured software float. The owner's four alternatives are Proposed rows; the costs and risks below come from the tables above and from the engine as it is.

- **[D-1110](../ledger/engine.md#D-1110): keep fixed point, no FPU flags.** No work and no risk to sound. The recursive kernels stay slower than float would be: six resonator modes 441.6 cycles a sample against 206.6, two biquad sections 88.8 against 67.7, the older two-pole modes 297.2 against 117.0. Long recursive tails keep needing rounding care in fixed point: the Resonator's ring that rounding held up for ever ([D-1109](../ledger/engine.md#D-1109), #840) and the floor fixes in flight. The 64-bit multiply erratum's exposure stays as listed above.
- **[D-1111](../ledger/engine.md#D-1111): FPU flags on, float at control rate.** The flags change no code until code uses float (the normal build is byte for byte the same), so turning them on is free. Per-block work (coefficients, `exp2`, conversions from Hz, the 64-bit divisions of `div64.c`) could then be float at 2 to 3 cycles an operation or about 200 cycles a libm call. The gain is small next to a block's million cycles, but the code gets simpler. Each such change must still match the browser engine within the golden kits' tolerances, and a change in a coefficient's rounding changes the sound bit for bit, so `tools/engine_exact.sh` can no longer prove such a step exact. Risk: low.
- **[D-1112](../ledger/engine.md#D-1112): float inside recursive kernels only.** The biggest gains for the least change: the Resonator about 235 cycles a sample faster per instance (2.9 % of a core), filters 20 to 30 % faster, and a decaying float state reaches zero by gradual underflow at no extra cost (subnormal operands cost nothing here), so no step-toward-zero or floor fix is needed. Signals between modules stay Q16.16, so the patch format, buffers, sharing and the AOT code stay. Cost: each kernel converted is a rewrite of that module in C with new golden expectations (its output changes in the last bits), a check on the rig and a listening check; the conversions at the module's edges cost 2.3 cycles each.
- **[D-1113](../ledger/engine.md#D-1113): a float audio path.** A rewrite of `engine.c` (about 11,700 lines), its golden kits and bit-exactness rules, the AOT generator, buffer budgets (a float buffer is as big as a Q16.16 one) and the CPU model, then a listening check of every factory patch. Phase accumulators and table oscillators get slower in float (17.3 against 28.5 cycles a sample for the parabolic sine), so they would stay integer; most of the engine's 1,851 inlined 64-bit multiplies would go, and with them most of the erratum's exposure. Risk: high; the gain over [D-1112](../ledger/engine.md#D-1112) is mostly in modules that are cheap already.
