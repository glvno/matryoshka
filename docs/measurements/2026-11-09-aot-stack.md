# Oracle V compiled-code stack check, 2026-11-09

The ahead-of-time (AOT) startup fault is a stack overflow on the second core. The generator now puts each member's work in its own non-inlined function. Both AOT-only and AOT plus RAM placement pass the focused emulator regression, cold starts and Oracle V playback on the registered FM-1. Both switches remain off in normal builds.

The tested firmware is commit `b140959e940c24b6d665fa7854dd663cf66b22f0`, [CI run 42689178479](https://github.com/glvno/matryoshka/actions/runs/42689178479). [Raw results](2026-11-09-aot-stack.json) include package hashes, switches, stack-check output, core health and every playback sample. The original failure's [hardware record](2026-11-09-rig-experiments.md) uses CI run 42673451565.

## Cause and fix

The JieLi compiler reserves separate stack slots for each member's input arrays and signal temporaries when a generated segment puts them all in one function. Oracle V's per-part segment reserves 2,388 bytes before calling the general module processor. At the first observed guard crossing, the call chain has reserved 3,760 bytes against a 3,328-byte allowance. This is the first crossing, not the maximum the unguarded call chain could reach.

The new member functions release that temporary storage before the next member runs. The per-part segment's own frame falls to 140 bytes. Member order, arithmetic, selector preparation and fading, feedback reads and final outputs remain the same. The stack allocation, hardware guard and one-core fallback are unchanged.

Stack paint counts memory written, so it misses reserved space that has not yet been written. Ordinary emulator runs do not enforce the hardware stack guard. `tools/aot_stack.sh BIN ELF` now single-steps core 1 and stops when its user stack pointer crosses the guarded lower bound. It also requires execution at the compiled lane-job entry on core 1, a bound compiled instance, completed playback with nonzero audio and healthy self-tests. An interpreter build is rejected unless `--interpreter` explicitly selects the control mode. This check runs locally, not in CI, and does not measure hardware timing.

## Checks

- Both original AOT binaries fail the new stack check before any notes, in the general module processor. Both fixed binaries pass through four and eight held notes. The interpreter control passes.
- Both fixed builds pass all 19 emulator boot checks, including the editor link and update handshake on their matching bridge builds.
- Host comparisons produce bit-identical output with compiled assemblies enabled and disabled, including parameter changes, patch changes, two compiled instances and threaded execution.
- The owner physically powered off and unplugged the registered rig after each candidate install. Each build then played Oracle V at 0, 1, 4 and 8 held notes, ten seconds per phase, with transport stopped and running: 80 seconds of sampled playback per build. Every phase reloads the patch. Both cores were checked before playback and after each four-phase group.
- Neither build reported a failed self-test, refused job, late audio half, shed voice or overload mute. The raw core diagnostics record the stack paint after playback.

Each comparison image is 559,688 bytes of its 581,564-byte flash slot, leaving 21,876 bytes. The RAM variant places 15,168 bytes of code in its reserved RAM region, leaving 240 bytes there. These are build measurements, not proof that another assembly will fit. The normal, size-only and RAM-only binaries are unchanged between CI runs 42688236500 and 42689178479 because their compiled-assembly switch is off.

This is a focused startup and short playback check, not a long soak, a matched performance comparison or a multi-instrument capacity result. [Issue #808](https://github.com/glvno/matryoshka/issues/808) retains those performance and capacity checks. No voice count, CPU estimate or default build switch changes here.
