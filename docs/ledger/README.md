# Decision ledger

This folder holds every decision made about Matryoshka, as rows with stable `D-###` IDs. It describes only the current state; git is the archive. If a decision is not a row here, it has not been decided. Agents do the clerical work of keeping it current; people decide and review.

Read this page before adding or changing a row. The prose rules are in [STYLE.md](STYLE.md); the terms this project uses in a specific sense are in [vocabulary.md](vocabulary.md). The ledger's own rules are rows in [process.md](process.md), so they can be amended the same way as anything else.

## What gets a row

A choice gets a row when **someone else would need to know it to do their work correctly, and it could reasonably have gone another way.** Concretely, any of: a new dependency, vendor, or service; a data shape or file format; an interface or contract between components or teams; a convention everyone must follow; a behavior change that had alternatives; who owns or decides something; a scope call (in or out of a release).

Not a row: a refactor, a rename, a bug fix, a choice with one reasonable option, an implementation detail nobody outside the file cares about, and anything still being argued — that goes under *Not yet settled*.

One row per ruling — never per commit, per file, or per meeting. When in doubt, log it as `Proposed` for a named decider. A wrong proposal costs a reviewer ten seconds; a missing ruling costs the next reader an afternoon. ([D-005](process.md#D-005))

## The files

One markdown file per subject. Every subject file has three parts, in this order:

1. **A paragraph of current state** — what a newcomer most needs to know about this subject today, with the rows it rests on linked.
2. **The table** — the rulings.
3. **`## Not yet settled`** — the questions we know we have not answered, each with the ticket or link where it is being worked. These are not rows. Nothing here has an ID.

Each file owns a block of IDs, declared on a line under its title (`IDs: D-050–D-099`), so the ID alone tells you which file a row lives in. A file that fills its block gets a second one on the same line, after a comma (`IDs: D-400–D-449, D-750–D-799`). ([D-003](process.md#D-003))

Files that are not subject files:

- `README.md` — this page.
- [`STYLE.md`](STYLE.md) — how rows are written.
- [`vocabulary.md`](vocabulary.md) — the project's terms, one `### Term` heading each. A term used in bold in a row links here.
- `backlinks.md` — generated by the checker; lists every place in the repository that refers to each row. Never edited by hand. ([D-007](process.md#D-007))
- [`process.md`](process.md) — a subject file like the others, whose subject is this ledger. Block `D-001–D-049`.

The factory-specific controls and patch points are in [fidelity.md](fidelity.md), block `D-700–D-749`.

## The row

Five columns: `ID | Decision | Status | Date | Source`. ([D-004](process.md#D-004))

```markdown
| ID | Decision | Status | Date | Source |
|---|---|---|---|---|
| <a id="D-093"></a>D-093 | The status-transition table is a contract: only listed transitions exist. **Amended 2026-08-20 (PO):** withdraw is out of MVP; a contributor asks the Publisher to return a request. | Decided, amended | 2026-07 → 2026-08-20 | PR #41; issue #58 |
```

- **ID** — `<a id="D-093"></a>D-093`. The anchor is what makes every mention a link. The checker adds it if you forget.
- **Decision** — the ruling, in current-state words, following [STYLE.md](STYLE.md). Never "we used to". Amendments are written inline: `**Amended <date> (<who>):**` followed by what changed. The wording before the amendment is one `git log` away.
- **Status** — exactly one of:
  - `Decided` — the decider has ruled.
  - `Decided, amended` — ruled, then refined in place. The Decision cell carries the marker; the Date carries both dates.
  - `Proposed (decider: <name>)` — logged by someone who is not the decider, waiting for the named person. A proposal is real guidance until it is rejected.
  - `Superseded by [D-###](file.md#D-###)` — the tombstone. The row stays so the ID never dangles; its Decision cell says only where to look now.
- **Date** — `YYYY-MM` or `YYYY-MM-DD`; an amended row reads `original → amendment`.
- **Source** — where a teammate can find the ruling being made: a pull request, an issue, a commit, a document, a meeting note. Never a path into anything private, and never something only one person can open.

## Making changes

**A new row** takes the next free ID in its file's block and carries the anchor. While drafting you may write `D-TBD` in the ID cell; a `D-TBD` row never merges.

**An amendment** edits the row in place: add the `**Amended <date> (<who>):**` marker to the Decision cell, set Status to `Decided, amended`, and make the Date `original → amendment`. Amend when the ruling stands but a fact in it changed. Only the decider amends; anyone else proposes the amendment text in the pull request and says so.

**A reversal** mints a new row with the new ruling and turns the old row into a tombstone: Status `Superseded by [D-new](file.md#D-new)`, Decision cell reduced to a pointer. The old wording is deleted, not struck through, and not moved to a history section. ([D-002](process.md#D-002))

**A question you cannot answer yet** goes under `## Not yet settled` with the ticket where it is being worked. When it is answered, it becomes a row and leaves the list.

**A new term** is defined in [vocabulary.md](vocabulary.md) before it is used in a row.

**Disagreement.** When a row and the code disagree, never fix it by silently editing one side to match the other. Put both in front of the row's decider — in the pull request, or as a `Proposed` amendment — and let them rule. ([D-010](process.md#D-010))

## Citing rows

In documents, every mention of a `D-###` is a link to its row: `[D-093](docs/ledger/edit-pipeline.md#D-093)`. Mentions inside code spans stay bare. Cite with the status: `([D-093](docs/ledger/edit-pipeline.md#D-093), Decided)`.

In a reply to a person, do the opposite of what the documents do: give each cited ID a short parenthetical summary of the ruling *and* the link, because a chat is ephemeral and cannot drift the way a restated rule in a document can.

## Before a pull request: the staleness check

Before opening a pull request that touches files outside `docs/ledger/`:

1. `python3 tools/ledger_check.py --changed origin/main` lists every row and every doc line that cites a file you changed.
2. For each, read the row and the diff and classify it: **still true**; **stale** (the ruling stands, a fact in it changed — amend); or **contradicted** (the branch does what the row says not to, or the reverse — follow the disagreement rule above).
3. Read your diff for choices that pass "What gets a row" and have no row. Add them, `Decided` if you are the decider, `Proposed` if not.
4. Anything decision-shaped in your pull-request description or commit messages that is not a row becomes one. Discussion belongs in the ledger, not in pull-request comments.
5. `python3 tools/ledger_check.py --fix`, then commit what it changed. The ledger edits ride in the same pull request as the code. ([D-009](process.md#D-009))

## The checker

`tools/ledger_check.py` enforces the mechanical rules on this page: file structure, ID blocks and uniqueness, status and date forms, every mention a link, vocabulary links, and a fresh `backlinks.md`. It runs in CI and must pass before merge. ([D-008](process.md#D-008))

```sh
python3 tools/ledger_check.py            # check; exit 1 on any finding
python3 tools/ledger_check.py --fix      # anchor rows, link mentions, regenerate backlinks, then check
python3 tools/ledger_check.py --changed origin/main   # rows and doc lines citing files this branch changed
```

Files the checker should not scan (generated docs, vendored text) are listed one glob per line in `docs/ledger/.checkignore`.
