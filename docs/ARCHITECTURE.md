# Architecture and plan

## Goal

Patch a small modular synth in the browser, run it on an M-VAVE FM-1. No FM engine, sampler, sequencer or UI from Felucca: only its flashing path and its hardware layer.

## What the FM-1 is (as far as known)

From the Felucca and FM-1 reverse-engineering projects: a JieLi AC791N SoC (pi32v2 core), 240×240 colour LCD, 27 keys, 7 knobs plus volume, USB MIDI/audio, TRS MIDI in, battery. CPU clock, RAM and flash sizes are **not verified** here; Felucca's `firmware/app.ld` and `tools/build.py` hold the memory map (app slot 0x8DFBC bytes, app RAM + a pool region).

## Flash path (reused from Felucca)

1. Browser (or `tools/fm1_install.py`) talks SysEx over USB MIDI. The *device* asks for blocks of a "logical image" (the package minus 20 marker bytes) and the host answers.
2. Step 1: the running firmware verifies parts of the package and stages Felucca's update loader. Step 2: the loader reads the whole package and writes flash. Then the device restarts and the identity (`FM-1_<n>`) is checked.
3. A package is built by `tools/fm1pkg_make.py` / `tools/build.py` (app.bin + loader ota.bin + three JieLi SDK files). `buildFeluccaPackage` (`web/src/flasher/fm1pkg.js`) can patch an app.bin into the user's own official V15; the Flash view does not offer it (#161).

## Patch engine

`web/src/engine.ts` and `web/src/modules.ts` are the reference implementation: float DSP, 128-frame blocks, patch graph ordered by `processingOrder` (loops become one-block feedback). Module definitions (`ModuleDef`) are data and are shared by the editor and, later, the firmware.

**Sample rate.** The FM-1's I2S runs at 44118 Hz (M-VAVE's own board code, `fm1_open` `app/board/fm1_audio.h`, `FM1_AUDIO_HARDWARE_RATE`; nominally 11.2896 MHz / 256), so `ENG_SR` (engine.h) and `DEVICE_SR` (modules.ts) are 44118 since 1.1; before that the firmware assumed 44100 and played 0.7 cent sharp with times 0.04 % short. A 128-frame half buffer is 2901 us. The golden test renders the reference at `DEVICE_SR`. The browser keeps its AudioContext's own rate (48 or 44.1 kHz): the engine works in Hz and seconds at any rate, so it already sounds as the device does; a 44118 Hz context would only add a resampler to the output. The delay and reverb lines are fixed sample counts at `DEVICE_SR` (the firmware's arrays) and scale with the rate in the browser. USB audio out (usb.c, `FELUCCA_UAC`, on since 2026-10-21; not verified on a device): the FM-1 is a UAC1 recording device, 16-bit stereo at 44.1 kHz only (48 kHz needs Felucca's resampler table `uac_fir.h`, not in this repo: `FELUCCA_UAC_48K` 0, the format descriptor lists 44100 alone, SET_CUR is acknowledged and changes nothing). The isochronous endpoint is asynchronous: packets of 44 / 45 frames, one more or one fewer while the ring's fill at a render's start is outside 160..208 frames, absorb the 18 extra frames a second (about 18 longer packets a second). audio.c taps each half's I2S words >> 8 after the render; update mode presents the MIDI-only descriptors of a build without it (`usb_uac_switch`), the update loader never had it. Diagnostics: `m1_link.py uac`; host test `tools/usb_test.sh`.

## Firmware

Builds with `tools/build.py` (in CI: `.github/workflows/firmware.yml`; see BUILDING.md), flashes with the web flasher or `tools/fm1_install.py`.

- `firmware/src/engine.c` is the fixed-point port of `web/src/engine.ts` and `modules.ts` (all 13 modules, mono voice, CV inputs, feedback cables as one block of delay). Signals and parameters are Q16.16, oscillator phase u32, filter coefficients Q24, envelope Q30; sine, exp2 and tan come from tables (`tools/gen_dsp_tables.py` -> `dsp_tables.h`). No float anywhere. The 32x32->64 multiply and the 32-bit divide are hardware; 64-bit division (a libcall) is used only at block rate and on waveform edges.
- `firmware/src/defs.h` and `presets.h` are generated from the TypeScript definitions (`npm run export-defs` in `web/`): module/port/parameter indices and the factory patches in the binary format of `web/src/patchbin.ts`. Port and type indices are append-only.
- The audio ISR (`audio.c`) renders 128 frames per half buffer. MIDI program change n loads bank slot n, note on/off and CC 123 drive the voice. The LCD shows the patch name in the top bar; the measured CPU load (ISR time per half buffer, key scan and USB nested in it) is kept in `eng_us_last` / `eng_us_max` but no longer drawn.
- `tools/golden.sh` renders 11 patches with the TypeScript engine and the C engine (host build) and compares them. Smooth patches agree to about 0.1 % rms (-60 dB), patches with saw/square edges to 1-2 % rms: the Q16 pitch grid moves an edge by a fraction of a sample, which gives short spikes at the edges and no audible difference.
- Memory (one build since #59, 2026-10-18: the four-voice build is gone): one engine, 255 signal buffers (128 KB), 128 instances, 1536 parameter values (6 KB, `par_pool`: each module takes its type's parameters, twice that with a morph B side, and each instance its type's effective values, not `MAX_PAR` each; a patch that needs more does not load, error -8; `DEVICE.params` in the editor's budget counts the same, [D-369](ledger/engine.md#D-369)), one delay line of 521 ms (46 KB), one reverb, eight strings, a chorus and a granular line (88 KB), the 1.0 release build (release.yml run 39685196079, a25c1bf): image 242,056 B; RAM .data+.bss 16,416 of 24,576 B (8,160 B free); pool 377,544 of 417,792 B (40,248 B free; `tools/pool_sizes.sh`'s stand-in for the same commit: 377,542 B). Limits: 64 modules, 255 cables, 160 summed inputs, 320 sources, patches up to 3840 bytes (a bank slot is one 4 KB sector with a 256 B header); the HELLO reply says 64 / 255 / 1.

Measured on the FM-1: the 303 Acid factory patch (8 modules, one delay) uses 11 % of the audio budget (peak 12 %).

Patch transfer (M1-0.3): `web/src/protocol.ts` defines the SysEx messages (`F0 7D 4D 31 cmd payload F7`, payload packed to 7 bit): HELLO/INFO, patch upload in 384-byte CHUNKs with an ACK each, COMMIT with a CRC-16, STORE, live PARAM. `firmware/src/proto.c` implements it (host-tested bit-exactly by `firmware/test/proto_test.c` through `tools/golden.sh`); for where patches are stored see [D-257](ledger/patch-format.md#D-257). A failed commit leaves the previous patch running; STORE saves the live-edited parameters too. `web/src/device.ts` is the browser side (toolbar: Connect FM-1, Live, Send patch, Store on FM-1); `tools/m1_link.py` does the same from a terminal.

**Parameter inputs and the source matrix (patch format 2, M1-0.6).** Every module except the FM-1 panel and the output has exactly two parameter inputs, `p1` and `p2`, each with an attenuverter (-1..1; scales and inverts), and a matrix with the sources p1, p2, k1, k2, k3, k4 on one axis and the module's parameters on the other. A parameter's effective value is base + (block mean of p1 x att1 and of p2 x att2, for the inputs the matrix assigns to it) x (max - min), clamped. The four knobs k1..k4 are the FM-1's encoders: on the device the SELECT encoder steps through the modules of the patch, and K1..K4 change the parameters their matrix column assigns on the selected module (one click = 1/100 of the range, or the parameter's own step if larger; five times that when turned fast). The FM-1 panel module is the patch's only input and the exception that stays as it was (there is no separate MIDI module: the keys and USB MIDI are handled by the firmware, and by the browser host, and play the one voice that the panel module outputs as pitch, gate and vel; a saved `midi` module becomes the panel module on load): its parameters are k1..k4 themselves and its outputs feed the patch, so with it selected the knobs work as the panel knobs. Default matrix: p1, k1 -> parameter 1, p2, k2 -> parameter 2, k3 -> parameter 3, k4 -> parameter 4. Old (version 1) JSON patches with `<param>_cv` cables are converted on load. The editor keeps each card's two inputs and exposes input aliases on parameter slider thumbs. Per-parameter routing menus replace the checkbox grid, including attenuverter depth, macro ranges and hardware knob assignments. `ParamDef.input` identifies dedicated CV aliases; other thumb drops reuse or allocate p1/p2 through `parameter-routing.ts`. New sources never silently enter pins shared by unrelated parameters. The persisted matrix remains compatible; routing changes re-send the patch, while attenuverters, ranges and parameters are live.

**Preset bank (M1-0.8).** The firmware has the factory patches compiled in (`presets.h`, generated from `web/presets/*.json` through `web/src/presets.ts`; 25, see "Factory patches"). The editor's Library > Patches keeps the bank's offline copy (up to 64 patches: factory ones and the user's), orders it and sends it to the FM-1, or with a connected FM-1 writes, erases and lists its slots directly ("The Library" in the Emulator view's section below): each patch goes into one slot (`slotstore.c`, 64 slots over 66 flash sectors, header with name and CRC written last; see [D-257](ledger/patch-format.md#D-257) and "The bank" below) through the SLOT / SLOT_ERASE / SLOT_INFO commands, without being loaded. The PRESET knob (encoder 6) and MIDI program change step through the occupied slots; the top bar shows the patch name.

See [D-203](ledger/device-ui.md#D-203).

**Releasing (#164).** A release package is built by hand in CI: `gh workflow run release.yml -f version=1.0` (or `1.0-rc1` for a dry run) runs `tools/build.py --release 1.0` (identity `FM-1_710`, version `v1.0.0`; every 1.0.x shares `FM-1_710`, the version string tells them apart), the same no-warnings and pool checks and host tests as firmware.yml, and uploads `matryoshka-release-1.0` = `release-1.0/` (package, its `.json` sidecar, the app `.bin`, `SHA256SUMS`, licences, build log); the run summary has the image / RAM / pool line and the checksums. Then: `gh run download <id> -n matryoshka-release-1.0 -D build/release-1.0`; `npm run emu:smoke -- build/release-1.0/matryoshka-1.0-app.bin` on that exact build; install it on the FM-1 (`tools/fm1_install.py` or the Flash tab) for the owner's check; `npm run firmware -- build/release-1.0/matryoshka-1.0.fwsc` bundles those bytes for the Flash tab; tag `vX.Y.Z` on a commit whose `firmware/` and `tools/` equal the built commit's, and attach the `.fwsc`, `SHA256SUMS` and a zip of the folder to the GitHub release. `build.py` writes a `<package>.json` sidecar (version, identity, size, sha256) next to every package, because the package's image is encrypted and `sync-firmware.mjs` cannot read the version from it. Since 1.0, Pages no longer builds firmware: it publishes the committed package in `web/public/firmware/`. Since 1.2 it builds the newest release tag, not main, so the site always pairs an editor with the firmware it was released with (main may bump the patch format freely); pushing the tag deploys the release, and a web-only fix is a patch release that keeps the firmware package. A new factory patch (with its XL and engine) ships the same way, as a web-only patch release, and reaches the FM-1's factory slots with the next firmware release ([D-126](ledger/releases.md#D-126)).

**Hosting (1.0).** The web app is on Cloudflare Pages, https://matryoshka.lol/ (the Pages project `matry0shka`, the custom domain set in the Cloudflare dashboard, where Cloudflare also runs the domain's DNS; the domain is registered with Amazon Route 53). The project's own address, https://matry0shka.pages.dev/ (the site's address from 1.0 to 1.4), serves the same app. There, `web/src/site-move.ts` runs first: when the origin's localStorage holds no `matryoshka.*` / `modular-1.*` key it calls `location.replace` to the same path, query and fragment at matryoshka.lol and throws, so no other module runs and nothing is stored. With data, the app stays and `web/src/move-offer.ts` shows a bar at the top, "Move them there", which runs the hand-off below with the app itself as the sender (`sendMigration`); "Not now" or a finished move hides it at that address (`matryoshka.move-offer`, never handed over), and the command palette there has "Move to matryoshka.lol". The command palette's "Save browser backup" (any address) saves the forwarder's backup file. The `deploy` workflow (`.github/workflows/pages.yml`, in glvno/matryoshka: on a pushed release tag `vX.Y.Z` when it is the newest release, or by hand with an optional tag; nothing else deploys) checks out the newest release tag and builds its `web/dist` and runs `wrangler pages deploy web/dist --project-name=matry0shka --branch=main` through `cloudflare/wrangler-action@v3` (secret `CLOUDFLARE_API_TOKEN`, variable `CLOUDFLARE_ACCOUNT_ID`); on a manual run from main (the github-pages environment deploys only main) a second job then publishes `deploy/github-pages-forward/` to GitHub Pages, so the old address https://glvno.github.io/matryoshka/ serves only the forwarder (`index.html` and an identical `404.html`, so every old path lands on it). The address is written once in the app, `SITE_URL` in `web/src/site.ts` (share links made outside a page, the community search, index.html's link previews through `vite.config.ts`; a link made in the editor uses the address it is open at); `site.test.ts` checks that the forwarder names the same address. Elsewhere it is in the workflow (the project name), the README, the CHANGELOG, CLAUDE.md / AGENTS.md and the community issue form.
- **The forwarder** strips `/matryoshka/` and keeps the rest of the path, the query and the fragment (a share link's `#p=`). With no `matryoshka.*` / `modular-1.*` key in its origin's localStorage it calls `location.replace` at once; with some it shows "Matryoshka has moved" with **Bring my patches**, **Open without them** and **Download a backup** (a JSON file `{format: 'matryoshka-browser-backup', version: 1, from, saved, keys}`).
- **The hand-off** (`web/src/migrate.ts`) is window.open + postMessage, because an iframe of the old origin inside the new app would read partitioned storage in Chrome. The button opens the new address with `?migrate=1` (a user gesture, so not a blocked popup; not `noopener`). The app, seeing `migrate=1` and a `window.opener`, posts `{type: 'matryoshka-migrate-ready'}` to the opener once for each earlier origin (`MIGRATE_FROM`: `https://glvno.github.io`, `https://matry0shka.pages.dev`; the browser delivers only the one matching the opener); the sender takes it only from the new origin and the window it opened, and replies `{type: 'matryoshka-migrate-data', keys}` with targetOrigin the new origin; the app takes that only from an origin of `MIGRATE_FROM` and its opener, imports, replies `matryoshka-migrate-done` to that origin (the forwarder then says "Done, you can close this tab") and strips `migrate=1` with `replaceState`. No reply in 5 s: it stops listening and strips `migrate=1`, quietly. The data never goes into a URL. A test build may set `VITE_MIGRATE_FROM` (the old origin) and the forwarder takes `?to=` (the new address) only when it is itself served from localhost; production keeps both origins fixed. Neither side would survive a `Cross-Origin-Opener-Policy: same-origin` header on the new site (the opener would be null): do not add one.
- **The import** (`planImport`) accepts only `matryoshka.*` / `modular-1.*` keys with string values (a legacy name becomes `matryoshka.*` unless that is there too) and never overwrites silently: the lists (Your patches, the library, the bank, the browser-only bank list, tutorial variations) merge entry by entry, a different entry under a name already here is added as "name (old site)" in Your patches and the library and left out of the bank (its names are the FM-1's slots; 64 at most); any other value is taken when this page found no such key at its start, else the one here is kept (an open patch kept here puts the old one into Your patches). The page then reloads so every part reads the data (a share link's fragment is put back first), and a toast lists what came over and what was kept. The backup file goes through the same import from Load .json, or the palette's Import browser backup.
- **Analytics** are Cloudflare Web Analytics, cookieless, turned on in the Pages project's dashboard: Cloudflare adds its beacon at the edge, there is no script for it in the repository.

## Measured CPU budget (benchmark firmware, `firmware/src/bench.c`)

Per 128-frame block (2902 us of audio as counted then; 2901 us at the real 44118 Hz), interrupts off, 16 repetitions, 1 us resolution, run on a real FM-1:

| kernel | us/block | instances in 70 % of a block |
|---|---|---|
| osc, Q15 parabolic sine | 7 | 290 |
| 4x Q15 multiply-add | 9 | 225 |
| state variable filter, Q15 | 8 | 253 |
| osc, float | 489 | 4 |
| 4x float multiply-add | 444 | 4 |
| state variable filter, float | 340 | 5 |
| float to int16 per frame | 116 | 17 |

Conclusions: the core has no FPU (float links against `libcompiler-rt.a` soft float) and float is 40 to 70 times slower, so the audio path is **fixed point only** (Q15 samples, 32-bit accumulators, no float, no 64-bit division). Float is acceptable only at control rate (per block), and better avoided. The fixed kernels are tiny; real modules will cost several times their bare kernel (buffer traffic, modulation, CV), so plan for tens of module instances, and measure the real engine before promising more. The 1 us resolution makes the fixed numbers coarse (+-1 us).

## Estimated CPU load (the editor's budget meter)

The editor estimates how much of the 2901 us audio interrupt a patch needs (`web/src/cpu.ts`, `cpuEstimate`; the status line's CPU bar; over 100 % counts as over the FM-1 budget like a memory limit, `deviceBudget` in patchbin.ts). It is a model: cycles counted on a stand-in core, calibrated on whole factory patches measured on the FM-1; nothing was measured per module on the device.

- **Counting.** `tools/cpu/build.sh` builds `firmware/src/engine.c` for rv32im (clang + ld.lld, `-Os` as tools/build.py) with `tools/cpu/prof.c` as the driver; `tools/cpu/rv32.mjs` is a small RV32IM interpreter (cycles = 1 per instruction, +1 load, +2 taken branch / jump, +32 division) that reads the `ENG_PROF` hooks in `render_voice` (compiled out in the firmware) and attributes each module's input sums, parameter inputs (`apply_cv`) and processing. The FM-1's core is not RISC-V; the model only has to get the ratios right.
- **Scale (calibrated 2026-10-20).** `us = cycles / 233.4 + 23` per block, of 2901 us (`cyclesPerUs`, `fixedUs` in cpu-costs.json, frozen constants in cpu-costs.ts `SURVEY`, not re-fitted on each run). The 17 factory patches were measured on the FM-1 (`docs/measurements/cpu-survey-2026-10-20.json`, CI run 39541520839 on `device-diag`: the longest audio interrupt at rest and with 1 / 4 / 8 notes held over USB MIDI); against the estimate at the old scale a least-squares fit gives device % = 1.041 x estimate % + 0.8, so 243 / 1.041 cycles per us plus 0.8 % of the block (23 us) that the counted engine leaves out: the rest of the interrupt (key scan, USB poll), whatever the patch. The old scale is still counted as a cross-check (cpu-costs.json `calibration`): the M1-0.2 engine (b907693) running its 303 Acid with a note held peaks at 84,600 cycles per block, which took 12 % (peak) of the interrupt on the FM-1 = 243 cycles per us; the bench kernels above (4x MAC 9 us, SVF 8 us) give 258 and 243. `cpu.test.ts` holds every factory patch within -4 / +6 points of its survey peak; after large engine changes a new survey replaces the file and the constants.
- **Table.** `cd web && npm run cpu-costs` (`web/scripts/cpu-costs.ts`, ~10 s on a worker pool, `tools/cpu/pool.mjs`) writes `web/src/cpu-costs.json`: per module type the cost with defaults plus a grid over what changes it, found by trying every setting alone and with every input patched (choices, small integers, a number stepping above its minimum = a mode such as the oscillator's FM, numbers as interpolated points such as `coarse`, patched inputs, patched outputs); shared costs (summing, a parameter input and each parameter it moves, morph, bypass, per module, per block, per Output). Pitch inputs are fed C5 while counting (a square or saw oscillator costs up to twice as much higher up); inputs are fed by an oscillator and by a held gate, the worse counts. Rerun it after changing the engine.
- **Checks.** Every factory patch and factory assembly (in a new patch, its outputs into the Output and Main's keys / pitch / gate / velocity into its inputs, so it is heard and played) is counted whole, holding one note per voice of its largest poly group (idle voices are skipped, below; the estimate is the worst case, every voice playing), and its peak includes the note-on block; `cpu.test.ts` holds the model to those counts (never more than 5 % low, at most 15 % high). Exempt from the upper bound (`looseModel` in cpu-checks.ts): grain and compressor (their cost depends on what they are fed; the table holds the worst case, a slowly triggered grain module reads up to 3x high), a filter cut-off moved by an LFO, an LFO whose rate is patched (a knob may turn it up to where the pitch it modulates moves every sample), an envelope or glide into a pitch (charged as moving all block; it settles sooner).

The estimate is the worst case, every voice playing; on the device a poly patch costs about the same at rest (every part renders). Hera 6 and Algo Four were probably clipped by the overload guard (a part shed above 85 %, no flag), so their device figures are lower bounds. - **Oscillator increments** (2026-10-17): the C oscillator works out its phase increments (`exp2_scale`) only when its pitch input changes from one sample to the next (exactly the same output; golden kits unchanged). A pitch from Main or a Part holds still for a block, so it costs less than one that moves. The table's `moving` (cycles per block and unison copy, measured with an LFO added to the pitch) is charged by `cpuEstimate` when the pitch may change about every sample (`keepsMoving` = `slope` ≥ 0.5 Q16 steps per sample: oscillators, noise, envelopes, glides, Random walks anywhere upstream; an LFO by its rate x depth unless something is patched into it; a free sample-and-hold LFO steps once a cycle and is not charged; a Scale multiplies its input's slope by its gain).

### Where the cycles go, and the speed-ups (2026-10-18, branch `cpu-opt`)

Profiled with `cd web && npm run cpu-hot` (the counted peak of every check, `--save` / `--compare` for before / after, `CPU_ELF=` another build, `CPU_NOTES=n` fewer keys), `-- --types` (cycles per module type over every check), `-- --nodes NAME` (per module of one check), `-- --hot NAME` (per function and per source line, from a `-g` build symbolized by `llvm-symbolizer`; inlined code counts where it was written). `scripts/cpu-est-check.ts NAME` shows the model's view of a check, `scripts/cpu-model-vs.ts F.json` the model's error against saved counts.

- **Before (main at 9cb3053), over every check:** module work 83 %, parameter inputs 9 %, input sums 1 %, the block loop and the Output 7 %. By type: SVF filter 21 % (360 cycles per sample with its cv patched: per sample `svf_g` + `exp2_scale` + two `svf_stage`, each a 32-bit division), oscillators 14 %, the reverb 10 % (142 k cycles, a fifth of the budget, each), ADSR 7 %, the Main module 7 % (it filled twelve output buffers every block, plugged or not), modal 7 %, LFO 4 %. The software 64-bit division (`__udivmoddi4`, the compiler's call for every `int64 /`) was 6..12 % of a patch: `apply_cv`'s block means, every per-block setup (cut-off and rates in Hz, the reverb's decay, the modal body's modes, the part flaws), the poly-BLEP. The `mulq` / `mulr` helpers were not inlined at `-Os`.
- **Bit-exact speed-ups** (`tools/engine_exact.sh` renders every golden kit with the old and the new engine and compares them sample for sample; `firmware/test/exact_test.c` checks the division-free helpers against plain division on random and edge inputs): `HOT` (always inline) multiply helpers; `block_mean` (sum / 128 by shift, rounding as C does); `hz_turns` (Hz -> turns per sample in two 32-bit divisions); `div64.c` (64-bit division in 32-bit steps, Hacker's Delight `divlu` / `divdu`; it replaces libcompiler-rt's members in the link, so every 64-bit division in the firmware is faster, checked against the host's division); summed inputs copy the first source instead of zeroing; the ladder's states in registers and its stages written out; the oscillator and the free-running LFO pick their wave once a block (no `switch` per sample), skip sync handling when nothing is patched there, and get the poly-BLEP position from a reciprocal cached per increment plus one exact correction (`blep_pos`); the SVF works out its coefficients only when the cv value changes and its second stage only when `lp24` or `mix` is used; the reverb's and the modal body's states in locals (int16 / int32 stores could alias them) with the lines / modes written out; Main and Part skip fills into unconnected outputs.
- **Idle voices** (not bit-exact, the same rule in both engines, golden agrees): a part of a poly group whose gate is low, whose ADSR / level envelopes (at least one) have finished and whose outputs out of the group stayed within 6 / 65536 for a whole block goes idle: those outputs are zeroed and the part's modules are skipped until a note reaches it, except every 32nd block, which runs it and checks again (a part that sounds without its envelopes comes back within ~93 ms). A voice that sat idle starts its next note with its oscillators and LFOs where they stopped (free-running phases differ from before; 20 ms loudness within ~0.3..1 dB on the poly golden kits, up to ~4 dB in the beating of detuned voices). The estimate stays the worst case (every voice playing); with one key down Oracle V counts 19 % instead of 65 %.
- **Device compile pass** (`web/src/device-compile.ts`, the last step of `deviceView(p, true)`, used by `encodePatch`, `deviceBudget`, `cpuEstimate`, `deviceIndex`; the editor's engine runs the uncompiled patch so unplugged modules still show live values): modules nothing audible depends on are not sent (except before the last Random module, whose seed is its index); modules of a poly group whose inputs come only from outside the group (or from such modules) and whose outputs stay inside it, which read nothing per voice (not Part / Random / Main / Output, not a filter / ladder that may track the pitch, not a flaw target when the group has flaws) run once instead of once per voice. `device-compile.test.ts` renders every factory patch and assembly with and without it, sample for sample equal.
- **After, every check:** −28.6 % on average (Oracle V 91 % -> 65 %, Hera 6 84 % -> 55 %, Expander S 88 % -> 57 %, supersaw stack 88 % -> 47 %, Algo Four 92 % -> 81 %: its FM oscillators run the 2x oversampled path, not yet reworked). With that headroom the factory Oracle V went to 5 voices (81 %) and Hera 6 to 6 (77 %). Real-firmware check: the CI build (JieLi toolchain, `div64.c` in the link) of this branch and of main played the same 24 s script in fm1-emu with byte-identical audio before idle voices; the firmware's own CPU readout showed Oracle V's chord at 37 % instead of 47 %.
- **fm1-emu gap found on the way:** the JieLi compiler emitted an `if ((R & #h) == #i) goto` with a long forward branch that fm1-emu (7ca5b96) decodes only up to 13 offset bits (`if_r_h_eq_i_goto_i`, mask 0xe000.. instead of 0x8000..); the free-running LFO was moved into its own function so the branch is short. Worth reporting upstream.

## Polyphony: Voice allocators and poly assemblies (format 20; allocators 2026-10-17)

Polyphony works the way a polysynth's hardware does (2026-10-17, replacing the Part module and the voice settings on the assembly). The **Main** module's `keys` output is the keyboard's ribbon cable: the held keys, a jack kind of its own (`SignalKind` `keys`, only into a keys input: `kindsFit` in patch.ts). A **Voice allocator** module (`alloc`, modules.ts) is the CPU: its `keys` input takes Main's keys, its parameters `voices` (1..16; the FM-1 plays 8), `assign` rotate / lowest / reuse / reset, `legato` auto / off / on, `priority` last / low / high, `unison` and `steal` decide how the keys become voices, and its outputs `pitch` (with the bend), `gate`, `vel`, `index` (−1 first voice .. 1 last, 0 with one), `legato` (1 while the note began over a held one) and `jump` (the pitch step from the voice's previous note, in octaves) are per voice. An allocator without Main's keys plays nothing. A **poly assembly** (`AssemblyInst.poly` = `PolyCards`: only the cards' `flaws`) is a rack of voice cards: its member modules, nested plain assemblies included, run once per voice of the allocator that feeds it (`allocatorOf`: the first allocator with a cable into a member that runs per voice, else one inside it), voice i on card i; one that no allocator feeds runs once. Delay, reverb, chorus, granular and the Output (`SHARED_TYPES`) and allocators run once even inside one. A poly assembly cannot sit inside another. Rules and helpers: `web/src/poly.ts` (`polyGroups`, `copiesOf`, `allocatorOf`, `deviceView`, `polyOfModule`, `setPoly`, `makeRoom`).

**Signals.** An allocator's output into a poly assembly it drives reaches voice i on card i; into a module that runs once it is the sum of its voices. A cable leaving a poly assembly carries the **sum of its cards** (a shared reverb hears the chord); a cable entering one reaches **every card**, as a polysynth's panel reaches every voice (one LFO sweeps all notes). Between two poly assemblies the receiving cards each get the sum of the sending ones. **Paraphonic mix (#125):** when no card gates its own sound (nothing inside the assembly hears the allocator's gate or legato: the gate goes only to modules that run once, say one shared envelope, as in Vernon 100), every card sounds whether it is played or not; its audio leaving the assembly is then weighed by 1 / cards (Q16, engine.ts `paraMix` = engine.c `para_w`), a fixed mixer, so the voice count does not change the level. Cards that gate themselves (an envelope or a gate-driven VCA inside) are summed as they are. One allocator may drive several poly assemblies (the same voices, layered: a Prophet-10's two layers); several allocators may share Main's keys (a pad and a bass, each with its own voice count).

**Device form** (`deviceView`). The engines and the FM-1 run the form from before allocators: every allocator becomes a **Part** module (`part`, engine only, not offered in the editor) in each poly group it drives; the first takes the allocator's id and place in the module list (module indices of the other modules stay the patch's: Live parameter changes address them), the others are appended. Each group carries the allocator's settings plus its cards' flaws (`PolyCfg`) and allocates the notes itself; groups with the same settings allocate the same way. An allocator's cables into modules outside its groups come from its first group's Part (the sum); one that drives no group gets a group of its own, or, with one voice played the keyboard's way, is a Part outside any group (the shared keyboard). Keys cables and allocators without keys are dropped. The binary (format 21), the C engine, the budget meter and the CPU estimate all take this form, so `firmware/` did not change; the golden kits' binaries and renders were byte-identical before and after. **Unison**: every voice plays the one note the priority picks (`monoUpdate` / `mono_update` on every part, with the same stamps); bit 7 of the group record's legato byte, and only then is the binary format 22 (`ENG_PATCH_VERSION` 22, compat 21; a patch without unison stays format 21 byte for byte). Golden kit `alloc-unison`.

**Notes.** Each poly group gets every note. Everything outside the poly groups runs once and plays the **shared keyboard**: Main's `pitch` / `gate` / `vel`, one note, the last held, legato. The editor's **poly** button (`setPoly`) puts a Voice allocator inside the assembly (it runs once there and travels with the assembly into the library), patches Main's keys into it (a `keys` jack on the card) and moves the Main pitch / gate / vel cables into the assembly onto it; turning poly off moves them back. The assembly card's settings show the voice count (the allocator's, read only there) and the flaws; the allocator's card has the rest. Older patches and definitions are converted on load (`migrateParts`: each Part becomes an allocator in its place with its poly assembly's old settings, or one voice outside one, and Main's keys go into it; `migrateDefParts` exposes its keys on the definition's card).

**Allocation** (`engine.ts groupOn` / `monoUpdate`, `engine.c group_on` / `mono_update`, identical). One part: the held keys form a list, the sounding one is the last, lowest or highest held (`priority`); a change of key while the gate is up is legato (`legato` auto and on keep the envelopes running, off restarts them). Several parts: a key already down on a part keeps it; else a free part by `assign` (rotate: the next in turn; lowest: the lowest-numbered; reuse: a free part whose last note was the key, else the one free the longest); with none free one is **taken over** by `priority` (last: the oldest note; low / high: the highest / lowest sounding note, and only for a lower / higher key, otherwise the key does not sound). A taken-over part outputs one low gate sample at the start of the next block (`retrig`, cleared after every block) unless `legato` is on, so its envelopes restart.

**Reset and no-steal allocation.** `assign: reset` rotates while keys overlap and starts again at voice one after every input key is released. A key whose voice was stolen or refused still counts as held. With `steal: off`, a new key is ignored when every polyphonic voice is held. It is not queued for later. A repeated key keeps its voice, and a released voice is available immediately. Single-voice and unison modes retain their note-priority behavior. Defaults keep stealing on and preserve the three existing assignment modes. See [D-441](ledger/modules.md#D-441), Proposed.

**Unison count.** Voicing's `stack` parameter selects how many of its existing voices play the priority note in unison. Zero means all voices. The polyphonic count stays unchanged, and a count larger than that pool uses the whole pool. Editing the count updates held unison notes immediately; the device does not reload the patch. The appended `unison` output reports the mode independently of the gate. Oracle V XL exposes `uni voices` and gates its detune and manual chord offsets with that output. Chord learning remains separate work. See [D-443](ledger/modules.md#D-443), Proposed.

**Shared unison.** The `share` choice divides the unison pool equally over held notes, with spare voices released. Last, low or high priority chooses notes when more keys are held than available voices. The selected notes are assigned in ascending pitch order. Io 4 therefore plays four voices for one key, two each for two keys, and one each for three or four keys. This is its UNISON II behavior; the full four-way assignment interface is still separate work. Both engines retain all 128 MIDI keys in their held-note lists. See [D-444](ledger/modules.md#D-444), Proposed.

**Lowest/highest voice outputs.** Voicing and Part append `low` and `high` gates. They mark the lowest and highest assigned notes among held voices in each group. Released voices and refused notes do not qualify. A mono voice is both, and every tied unison voice qualifies. Existing outputs retain their indices and behavior. Algo Four XL uses these gates for its named LOW/HIGH/KON pitch-bend control. KON applies bend to every voice, including release tails. Its breath and foot inputs use Main CC 2 and CC 64. See [D-442](ledger/modules.md#D-442), Proposed.

**Random.** The **Random** module (`mode` fixed / walk, `rate`) gives each copy its own value −1..1: fixed is `hash32` of the instance seed (`instSeed` = module index and part), walk an integer random walk (`walkInit` / `walkStep`: a new Q15 target every `hold` = round(sr / (128 · rate)) blocks, each block 2 / hold of the way there; it steps every block in either mode). Bit for bit the same in both engines. It replaces the Main module's former `tol` / `drift` outputs and the oscillator's `drift`: a fixed Random into a cutoff is a voice card's tolerance, a walking one into `fine` an oscillator's drift.

**Part flaws** (2026-10-16, replacing the `unit` seed): each part of a poly assembly has its own flaws, set by hand in the editor's flaws card (`web/src/flaws-panel.ts`, opened from `flaws` in the poly settings; Randomize gives every part small ones). `PolyCfg.flaws[i]` = `PartFlaw` of part i (patch.ts; missing = none): `detune` −50..50 cents and `drift` 0..100 % (a slow walk, `driftSeed(group, part)`, a new target every 2 s (`DRIFT_RATE` 0.5 Hz), up to ±20 cents at 100 %) are added to that part's Part `pitch` output (`flawQ16`, integer and the same in both engines); `bright` −24..24 semitones multiplies the cutoff of every filter / ladder in the part (2^(st/12)), `env` −50..50 % the a / d / r of every ADSR and r1..r4 of every envelope ((100 + env) / 100), `level` 0..100 % the gain of every VCA (`FLAW_TARGETS`), on the copy's effective value after modulation, clamped to the range (engine.ts `applyFlaws`, engine.c `apply_flaws`). Golden kit `part-flaws` (every flaw at its ends); dropping detune or `apply_flaws` in C fails it.

**Old patches** are converted on load (`migrateVoicing` in poly.ts, inside `validatePatch`): `voices` > 1, non-default Main legato / priority or cables from spread / legato / jump become an open poly assembly "basic poly" (assign reuse, the old allocation) around the old per-voice set plus a Part; Main tol / drift become Random modules; an oscillator's drift becomes a walking Random into `fine` through a free pin (depth = drift / 2 / 200). Saved assembly definitions get the same treatment (`migrateDefDrift`). A stored `unit` (format 20) is dropped.

**Binary format 21.** Header byte 3 is the number of poly groups G (0..4); after the 8 header bytes come G records of `GROUP_REC` = 44 bytes (parts, assign, legato, priority, then for each of 8 parts: i8 detune, u8 drift, i8 bright, i8 env, u8 level), then, with any group, one byte per module: its group (0 = runs once). The module records start at `eng_records_at` (engine.h). Stored patches older than `ENG_PATCH_COMPAT_VERSION` (31 today) are refused, and the slot plays the fallback patch ([D-251](ledger/patch-format.md#D-251)).

**Engines.** `engine.ts`: a `Group` per poly assembly (plus the keyboard), a node has one `Inst` per part of its group, `gather` sums another group's instances. `engine.c`: `grp_t E.grp[0..ngrp]` (0 = the keyboard) with their parts in `E.pv[]` (`ENG_NPV` 33), `node_t.grp`, `cur_g` / `cur_pv` while a node's instance renders; inputs from another group's per-part output get one summing source per part.

**Limits on the device.** Signal buffers: 255 (`ENG_NBUF`), one per connected output and instance plus one per summed input; instances 128 (`ENG_MAX_INST`). `eng_load` returns -6 / -7 when a patch does not fit. `deviceBudget` in `web/src/patchbin.ts` counts the same way (copies per poly assembly) and the poly settings' `parts` picker shows it (red when too big). CPU per part on the device: not measured.

**Controls.** Editor: the poly button on every assembly header, the settings as pickers on the collapsed card and as a strip under an expanded frame's header; ×N badges on the cards that run per part. Device: see [D-220](ledger/device-ui.md#D-220).

**Golden vectors.** The kits that used `voices`, Main voicing or oscillator drift are built the old way and loaded through the conversion (`makeOld` in `web/scripts/golden.ts`); `poly-layers` (three layered groups with different assign / priority / legato, a note sequence that tells the assign modes apart, cross-group FM, a shared filter and delay) and `part-random` (Part index, fixed and walking Random, part flaws, a Random outside the group) and `part-flaws` use poly assemblies directly. Changing any byte of a group record makes them fail.

## FM oscillator

The oscillator has two ways to make FM-style timbres: the `pm` input (phase modulation by another signal, the `pm` parameter is the index in radians per unit of input, 0..8) and the `fb` parameter (operator feedback: the raw wave modulates its own phase, by pi radians per unit of the average of the last two samples at `fb` = 1, the DX7's level 7). Feedback inside the module replaces the one-block-late feedback cable for this purpose.

**FM mode.** When `pm` is connected with an index above 0, or `fb` is above 0, the oscillator runs at twice the sample rate: two waves per frame (the `pm` input interpolated linearly between frames), then a polyphase half-band decimator of four first-order allpass sections, two per path (coefficients Q16 `5376 17567 35764 55599`, flat to 0.22 fs, 41 dB down above 0.28 fs: 19.4 kHz and 24.7 kHz at 44.1 kHz). Sidebands between the old Nyquist and the oversampled one are filtered out instead of folding back; on bright high notes the non-harmonic (aliased) energy drops from -27..-33 dB to about -41 dB, the decimator's floor. Both engines use the same coefficients; the fixed-point one keeps the allpass states in Q16 (`inst_t.s.osc`). Cost: about 2.3 oscillators. The plain path (no pm, no feedback) is unchanged, so patches without FM render exactly as before.

Two things to know when patching: the band-limited signal overshoots the level (up to about 1.4x on very bright settings), so leave headroom before the output; and the feedback loop runs at the oversampled rate, so the sound for a given `fb` is a little brighter than the same number on a 44.1 kHz implementation.

Binary patch format 7: the oscillator record grew by the `fb` parameter.

## Assemblies (editor only)

`web/src/assembly.ts` is the model, `web/src/assemblies.ts` the user's library (Library > Assemblies) and the factory set (`web/src/assemblies/*.json`), `editor.ts` the canvas side. The patch stays flat: `Patch.assemblies` is an overlay of entries `{ v, id, name, label, x, y, open, modules, inputs, outputs, params }` where `modules` are ids in `patch.modules`, `inputs` / `outputs` are exposed inner ports (`{ module, port, label }`) and `params` promoted inner parameters (`{ module, param, label }`). Cables always join inner ports, so the engine, `encodePatch`, the protocol and the firmware only read three things of the overlay: an assembly's `poly` setting (see Polyphony), the device pages and the device extras ([D-253](ledger/patch-format.md#D-253)); `fixAssemblies` (called by the editor when a patch comes in) drops entries that do not fit the modules and reports them. Members are plain modules, never the panel or an output, and never in two assemblies; `v` is there so an entry can later name another assembly as a member.

Rules: `reconcile` keeps an assembly consistent after every structural change (departed members leave, every inner port with an outside cable is exposed, labels of ports that stay are kept); `hidePort` refuses while an outside cable uses the port; a module that joins (`addMember`) retracts the exposures that only its cables had caused. A saved assembly (`AssemblyDef`, `format: "matryoshka-assembly"`) is a small patch with local ids 1..n, positions from the top left member, the cables between members, exposed ports and promoted parameters, parameter values as defaults, p1 / p2 matrix and attenuverters, and no K1..K4 assignments (also stripped on insert, since knobs belong to the patch). `insertAssembly` gives fresh ids, places the collapsed card at the next free grid slot; there is no module cap (the budget meter flags a patch over the FM-1's 64 modules, [D-625](ledger/editor.md#D-625)). A patch's own modules (`EXCLUDED_TYPES`: `fm1`, `output`) never belong to a building block: `makeAssembly` refuses them, the editor's "Make assembly" drops them from the selection first ("Main and Output stay outside"), and `validateAssemblyDef` runs `stripPatchIO` on every file or library entry (the modules, their cables, exposed ports and promoted parameters go). `AssemblyDef.category` is a factory definition's shelf (`CATEGORIES` in assemblies.ts: Drums, Voices, Effects, Textures, Utilities, set per `asm()` in gen-assemblies.ts; the user's own have none and sit on "Your library"). The toolbar's "Insert assembly" opens `AssemblyBrowser` (browser.ts: shelves left, entries right with `summary` and `portsOf`, a fuzzy search across shelves via fuzzy.ts, Enter or a click inserts); the module select inserts on pick and is grouped by `MODULE_GROUPS` in main.ts. "New patch" = `newPatch(DEFS)`: Main at the top left, Output three grid columns right, unwired (`emptyPatch` stays for tests); outside the tutorial it first opens "Start with an engine" (engine-start.ts, #160: a tile per factory engine, a pick inserts it wired; Esc or "Start from an empty canvas" is the bare patch). The Patches and Assemblies tabs are one Library tab (`#library`; `#presets` / `#assemblies` in the address still open it). The editor keeps a 40-step snapshot undo of the patch JSON for structural changes (Ctrl/Cmd+Z, Shift for redo). On the canvas a collapsed assembly is one card whose port dots carry the inner module ids, so dragging cables works unchanged; an expanded one (the card's expand / collapse button) is a frame laid out around its member cards, which get the expose / pin toggles, and dropping a card into or out of the frame changes membership.

Several rows at once (#186): in pick mode (the frame's `card · N`) and Arrange mode (the card menu's Arrange the card) the parameter rows can be selected (`Editor.rowSel`, `module:param` keys, kept per mode and cleared when the mode changes): a band from the empty canvas or a card's empty space, Shift-click a range, Cmd / Ctrl-click one row (inside the modes it only selects; outside, Cmd / Ctrl-click still shows or hides a row); Cmd / Ctrl+A selects every row, Esc clears the selection and a second Esc ends the mode. Jacks are never selected and stay one click each. Pick mode: Space / Enter or the bar's `show N` / `hide N` applies `pickRows` (any selected row hidden: all shown, else all hidden), a member card's header check box does the same for all its parameters (`pickState`: all / none / some), and `select all` / `select none` in the frame's bar act on every parameter at once. Arrange mode works on a tree of the card's rows (`web/src/arrange.ts`, tests `arrange.test.ts`): `layoutOf` reads the flat `ParamRef` list and `AssemblyInst.heads` (headings with no rows, each anchored to a row: before the section that row opens, or `after` the last row of that row's column) into columns › sections › rows, `pagesOf` cuts a section into pages as `groupStarts` does, the operations edit the tree and `setLayout` / `flatten` write it back (every factory card comes back unchanged). The editor draws the rows from the tree (`Editor.arrangeRows`) and, once they are laid out, an overlay (`.arr-ov`, `drawArrange`) over the card: a faint outline around each section (its heading and pages) and each page, the page's ⠿ handle in a strip on its outline's left, **+ heading** under each section and at each column's top (it stays when it has no rows; the FM-1 has no page for it), **+ page break** between two rows of a page, and the × of a break set by hand. The heading field shows the FM-1's name for its pages in mono, in parentheses (`fm1Name`). A drag has one landing line per place (`rowSpots` and the page and section spots, `nearestSpot`): a row lands at the start of a page (it opens the page: it takes over the page's flag), between two rows, at the end of a page, or into an empty section, never into another page that already has `PAGE_ROWS` knobs; a page's handle moves the page whole (between pages, a section's top or end, an empty section); a heading's grip moves its section (a column's top, between sections, a column's end; never above the rows a column goes on with). Every move first pins each page start (`pinPages`), so the pages around it stay as they were; a row that started a page hands the start to the next row. A selected row drags the selection as one block. Delete or the bar's `take off N` takes the selection off the card. Each of these is one undo step. On touch there is no band: a long press on a row starts a selection, taps add or remove rows, a selected row drags the block at once, a tap on the empty canvas ends it.

## Engines, voices, drums (#159, 2026-10-21)

The words the editor uses for assemblies, as the FM-1 community uses "engine" (the instrument a track plays):

- **Engine** (redefined 2026-10-23, [D-321](ledger/patches-and-presets.md#D-321), #189): an assembly that takes keys and makes audio: keys → voicing → voices. `web/src/engines.ts` derives it from the contents (`isEngine`, `defIsEngine`, `instIsEngine`), never from names or `category`: a `keys` input whose keys reach a Voicing module (`alloc`, labelled Voicing, was Voice assigner) or a Drum map (`VOICING_TYPES`), following keys cables through an Arpeggiator or a Steps track's keys out, and at least one `audio` output. Factory: 19 (8 Lire, Algo Four, basic poly, Briefcase 3, Canvas, drift poly, drum kit, Elvira 2, Expander S, Hera 6, Io 4, mono lead, Monolith D, Oracle V, Sallen 20, Silver Box, supersaw stack, Vernon 100, Wanderer).
- **Voice**: pitch + gate in, sound out: one note (pluck, kalimba, operator). Engines are built from voices; Poly turns one into voice cards. ("voices" alone in the web app still means polyphony.)
- **Drum**: gate in, one hit (kick, snare). The drum kit, which takes keys, is an engine.

The assembly browser and the palette put the engines on an **Engines** shelf, first among the factory shelves (`ENGINE_SHELF`, `shelvesOf` in assemblies.ts, derived, not a `category`): an engine leaves Voices, and one from another shelf stays there too (the drum kit is on Engines and Drums). Rows carry a gold ENGINE tag; the palette tags engines `engine` ("engine" / "engines" filters to them, as "assembly" does). `Editor.insert` wires an engine in the same undo step (`wireEngine`): Main's `keys` into its keys input (Main's keys may feed several allocators), and, when no cable goes into the Output, its audio into `l` / `r` (stereo: the outputs labelled l and r, else the first two) or `l` (mono). A loaded patch with nothing into the Output says "Nothing makes sound yet. Add an engine, then play a key." In user-visible text "engine" no longer means the DSP runtime ("audio" in error lines); the code keeps `engine.ts`, `engine.c`, `ENG_*`.

## Sync, glide, shaper, spread

- `sync` (a gate input) on `osc` and `lfo`: a rising edge through 0.5 sets the phase to 0 before that sample's increment; the previous sample is kept in the state (`s1`). The oscillator honours it in both the plain and the FM path.
- `glide`: `y += k (x - y)` per sample with the ADSR's rate curve (`env_rate`, 99 % in `time`); the fixed-point state is Q24 because in Q16 the step rounds to nothing while the output is still about 1 % short, which on a pitch is audible and broke the golden comparison.
- `shape`: `drive` (1..32, log) into soft (`1.5 x - x^3 / 2` to the knee at 1, then flat), hard (clamp) or fold (triangle of period 4, two's complement masking does the modulo in fixed point), then `level`. The peak is 1 in every mode. `sym` (-1..1) is added to the driven sample before the curve; `stages` (1..4) cascades the curve with `y = curve(2 y)` between stages (`shapeChain` / `shape_chain`), inside the oversampler when `os` is on. No state is added. Patch format 16 (two new parameters). Golden kit `wavefold` (fold, sym 0.3, three stages, oversampled, drive swept by an LFO): 2.0 % rel rms, the fold corners move with the sweep.
- `spread`: a per-voice panel output, `(2 v - (n - 1)) / (n - 1)` for voice v of n. Now the Part module's `index` (see Polyphony).
- Binary patch format 8: the two sync inputs moved `p1` / `p2` of osc and lfo, two module types were appended, the panel grew an output. `TYPE_COLOR` in `ui.c` has entries for the new types.


## Level/rate envelope, string, wavetable, chorus

- `env`: four levels and four times, Q30 state like the ADSR. A rising segment adds 2^30 / (r sr) per sample (so 0..1 takes `r`), a falling one approaches at the ADSR's `env_rate` and ends after `r` samples (the last 1 % is stepped so the next segment starts on time). Stages 0 (idle, tracks `l4`), 1..3, 4 (holds `l3`), 5 (release).
- `env8` (Env 8, the Casio CZ's eight-step envelope): eight levels and eight times, by `env`'s segment rules. Stages 0 (resting at the end step's level), 1..8 (the steps), 9 (holding the sustain step's level). A finished step goes to the hold when it is the sustain step and the gate is up, to rest when it is the end step, else to the next step. The gate's fall jumps from the hold, or from any step up to the sustain step, to the step after it (rest when the sustain is the end). `sus` off, or past `end`, runs every step through and ignores the gate's fall (Env L/R's one-shot). With 18 parameters its matrix and input-route masks in the binary are u32 (`maskBytes`, `eng_mask_bytes`; a type with 16 or fewer keeps u16), so pins move `sus` and `end` like any parameter. That makes `MAX_PAR` 18 and the firmware's node masks u32; the parameter values themselves take only their type's count from `par_pool` ([D-369](ledger/engine.md#D-369)). The firmware caches one step's rate divisions (`env8_rates`) and works them out again when the step changes or its rate moves. Golden kits `env8` (sustain mid-way, off, at the end; rates on an LFO) and `env8-poly` (four parts, the env flaw).
- `string`: a delay line of one period with a one-pole (`cl = 1 − 0.9 damp`) in the loop; per block from the block's first pitch: the period (clamped to 2..1102 samples), the loop gain `g = 2^(−log2(1000) · period / (decay · sr))`, and the fractional delay `period − (1 − cl) / cl` (the one-pole's low-frequency delay), read with linear interpolation. A rising gate loads a burst of `round(period)` samples. The loop is clamped to ±2. Firmware: int16 Q13 lines (`str_pool`, 8 × 1104 samples, 17 KB) written with first-order error feedback, because the loop would otherwise recirculate the rounding noise with gain 1 / (1 − g); golden `string` matches to 0.04 %.
- `wavetable`: `tools/gen_wavetables.py` defines 40 frames by their first 32 harmonics (cos / sin coefficients, normalized to a peak of 1), writes them as `web/src/wavetables.json` (the reference builds its tables from them at start) and as `firmware/src/wt_tables.h` (int16 Q15, 257 samples per frame, three mip levels of 32 / 16 / 8 harmonics, 61,680 bytes of flash). The mip is chosen per block from the first pitch (32 harmonics below sr / 64, 16 below sr / 32, else 8); frames are read with linear interpolation and crossfaded by `pos`. Phase modulation is the plain oscillator's (not oversampled). The fifth bank is EML COLOR: triangle, sloped square, square, saw and double saw an octave up. Its transition positions are interpolated, not calibrated to the original knob ([D-440](ledger/modules.md#D-440)).
- `chorus`: shared like the delay (`SHARED_TYPES`, `T_CHORUS` in the firmware's voice split); a 927-sample Q13 line, two taps `12 ms ± 8 ms · depth · sin`, the right one a quarter cycle behind, linear interpolation. One instance per patch (`ch_pool`).
- Pool budget: see "Voices and the shared pools" (the numbers of this batch were superseded by the merge with the four-voice firmware).

## Sequencer, clock divider, S&H, quantizer, pulse

- All five act on rising edges through 0.5 (Q16 32768), like `sync`. `seq`: ten parameters (the first module above eight, hence the u16 masks of format 9); `out` is `s[pos]` every sample, so the step's knob is live; the random direction uses the LCG of the LFO's S&H. `clkdiv` counts edges modulo 16 · div (a common multiple of div, 2, 4, 8) and starts at −1 so the first edge is a downbeat. `quant`: semitones = 12 · in − root, octave by floor division, the nearest of the scale's degrees or the next root; ties go down (the two engines can differ at an exact float tie, which modulation never hits). `pulse`: a sample countdown of round(time · sr).
- Golden `seq-clock` (clock -> divider -> pendulum sequencer -> quantizer -> oscillator, sequencer gate -> pulse -> ADSR, d4 -> sync) and `sh-random` (clocked S&H on noise -> pentatonic quantizer, a tracking S&H on the filter, a random sequencer on pulse width; 2 voices) pass at 1.5 % and 0.2 %: the edge decisions line up sample for sample.
## Pan, crossfade, vowel, phaser, digitizer, noise colour

- `pan`: l = in·cos((p+1)π/4), r = in·sin((p+1)π/4) with p = clamp(pan + pos, −1, 1), per sample (C: sin_turn at (p+1)/8 of a turn).
- `xfade`: out = a·(1−m) + b·m, m = clamp(mix + pos, 0, 1).
- `vowel`: three SVF stages (the normalized band output k·v1, peak 1) at the formant frequencies of A (730, 1090, 2440), E (530, 1840, 2480), I (390, 1990, 2550), O (570, 840, 2410), U (440, 1020, 2240) Hz with gains 1, ½, ¼; the position v = clamp(vowel + input[0], 0, 4) interpolates the frequencies linearly between neighbours once per block; k = 1/Q, Q = 2 + 18·res. The C version reuses svf_g / svf_stage and Q20 states like the filter.
- `phaser`: four first-order allpasses y = a(x − y₁) + x₁ with one coefficient a = (g−1)/(g+1), g = tan(πf/sr), f = center·2^(2·depth·tri), tri a triangle LFO at `rate` read once per block; the input of stage 1 is in + fb·(stage 4's previous output), clamped to ±8; out = in·(1−mix) + wet·mix. In C the coefficient is Q24 from one 64-bit division per block.
- `crush`: step 2^(1−bits), y = floor(x/step + ½)·step on the taken sample, held for `rate` samples (C: shift by 17 − bits).
- `noise` `color`: y += c·(white − y), c = 2^(−5·color) (color 0 is c = 1: the old noise bit for bit); the state is Q24 in C.
- Golden kits: `pan-xfade` (3 voices), `vowel-phaser`, `crush-color`.

## Unison

- `osc` parameters `unison` (1..5) and `detune` (0..100 cents, default 10): in the plain path (no pm, no feedback) the oscillator runs n phases, voice j detuned by detune·(2j/(n−1) − 1) cents (−detune .. +detune, symmetric), and outputs their sum / n (the peak stays at `level`; detuned copies beat). A sync edge restarts every phase. The FM path ignores unison (one voice). C: the extra phases are `inst_t.s.osc.ph[4]` (the union is sized by the delay's record, so nothing grew), one `exp2_scale` per voice per sample, sum × 1/n from a table. Binary patch format 11 (the oscillator record has 9 parameters). Golden kit `unison` (5 + 2 voices): 1.3 % rel rms (the detuned saw edges fall on different samples in float and Q16, as in the other saw kits).

## Frequency shifter

- `shift`: single sideband. A Hilbert pair (Olli Niemitalo's two chains of four second-order allpasses y = a²(x + y₂) − x₂, coefficients `HILBERT_A` / `HILBERT_B`; chain A's output delayed by one sample is I, chain B's is Q) and a quadrature oscillator at `shift` + cv·cvamt Hz (per block from the block mean of cv): up = I·cos + Q·sin, down = I·cos − Q·sin (the sign convention of this pair; verified by the test: a 440 Hz sine shifted by 100 comes out at 540 on `up`); each output is in·(1 − mix) + shifted·mix. Below about 20 Hz the pair's phase error lets a little of the other sideband through, as with any such design. C: a² in Q30 (`HILB_A2` / `HILB_B2`), each section in the two-state form w = x + a²w₂, y = a²w − w₂ (18 words of state), signals Q16, `sin_turn` for the oscillator, the increment from Hz as (hz << 16) / sr in u32 turns (a negative shift wraps). Golden kit `shift` (saw, LFO on cv): 0.4 % rel rms.

## MIDI performance controls

Main provides `bend` (−1..1), `mod`, `at`, `breath`, `sustain` and `foot` (0..1). Its `pitch` output already includes pitch bend at ±2 semitones. CC 1 drives `mod`, channel aftertouch drives `at`, and CC 2 / 64 / 65 drive `breath` / `sustain` / `foot`. Each control keeps its last value until another message changes it. Sustain and foot are patchable signals; the patch decides how to use them ([D-470](ledger/link-and-midi.md#D-470), Proposed). CC 16..19 edit the focused device page ([D-453](ledger/link-and-midi.md#D-453)).

The browser parses these messages in `input.ts`, and `Engine.bend`, `cc` and `aftertouch` store one set of values for every voice. Firmware dispatch in `midi_input.h` respects MENU > MIDI CHANNEL for these controls. `eng_ctl` stores their values and `m_fm1` writes the outputs. The new outputs are appended after the panel-button outputs, preserving existing port numbers. `MAX_OUT` is 19; module parameter records are unchanged.

## Extended oscillator waveforms

Oscillator adds sharktooth (the equal mix of its triangle and saw) and reverse saw (the negated saw). These are ideal waveforms after the Model D's triangle/saw hybrid and reverse saw, described in the [manufacturer's manual, oscillator bank](https://www.suonoelettronico.com/downloads/minimoog_manuale.pdf). They use the same edge smoothing, sync, unison and phase-modulation paths as the existing waves. The new choices use `top: 5` with the existing `max: 3`; old parameter routing and morphs retain their original range ([D-435](ledger/modules.md#D-435), Proposed).

## Audio-rate Ladder cutoff

Ladder's `fm` input adds a sample-by-sample cutoff signal to its existing `cv` input, whose value is averaged over the block. Both use `cvamt` in octaves. Coefficients are reused while the sample value stays the same. The new input follows `p1` and `p2`, so old patches keep their cable numbers, parameter records and sound ([D-434](ledger/modules.md#D-434), Proposed).

## Comb filter and modal resonator

- `comb`: the string's line (one period of pitch + coarse, 40 Hz lowest, linear interpolation, the damping one-pole's delay taken off the line) with signed feedback `fb` (−0.98..0.98) and no burst: y = clamp(in + fb·lp(y[n − period]), ±2), out = in·(1 − mix) + y·mix. C: `it->s.str` (buf, w, lp, err with the error feedback) and a string-pool line, so `ENG_NSTRING` is shared by strings and combs.
- `modal`: six two-pole resonators y = a·sinθ·x + 2r·cosθ·y₁ − r²·y₂ (impulse response rⁿ·sin(θn): a unit impulse rings at amplitude 1), partial i at ratio (i+1) + struct·(bar_i − (i+1)) with the free bar's ratios 1, 2.756, 5.404, 8.933, 13.34, 18.64; r = 2^(−log2(1000)/(decay_i·sr)) with decay_i = decay/(1 + 2·damp·i); amplitudes (0.3 + 0.7·bright)^i normalised to a sum of 1; partials at or above 0.45 sr are left out; states held to ±8. Coefficients once per block from the block's first pitch. C: g, c1, c2 in Q30, states Q20, rounded products; cos θ must be accurate near 1 (a Q16 cosine moved the pole by 1 % at middle C), so it is 1 − 2·sin²(θ/2) from a Q30 sine lookup (`sin_turn30`); r from `exp2_scale(1 << 30, e)`. Golden kits `comb` (saw, fb −0.85) 0.35 % and `modal` (gated noise burst) 2 % rel rms (the decay's table error shows up late in the ring).

## Phase distortion oscillator (`pd`, issue #351)

- After the Casio CZ ([D-431](ledger/modules.md#D-431)). A ramp u (0..1 per cycle of the note) reads a sine at the bent phase u + dcw·B(u). B is the bend at full DCW (the CZ's "digitally controlled wave"), the bent phase minus the ramp, straight between sixteenths of the cycle (`PD_SEGS` in modules.ts): saw (slope −3/7 to 7/8, then 3), square (±1, holding the sine at its peak and trough), pulse (7 to 1/8, then −1: held), double sine (the saw's bend in each half), saw-pulse (1/7 to 7/16, 7 to 1/2, then held). dcw = the parameter + the `dcw` input, clamped 0..1, per sample.
- Resonance I, II, III: a sine at 2^(dcw·`range`) times the note, restarted at each cycle start (at u times the ratio, so the restart lands on the ramp's phase), times a window of u: 1 − u, 1 − |2u − 1|, min(4u, 2 − 2u, 1). The ratio is worked out at the block's first and last sample (from dcw there) and runs in a straight line between, so a moving dcw costs no exp2 per sample.
- `wave2` (0 off) plays on the odd cycles; the cycle count runs whether it is on or not, and sync (a rising edge) restarts the cycle at the first waveform.
- Band limit, once a block from the first pitch: room = (sr / 4) / f. A bend's dcw is held to (room − 1) / steepness (steepness 3, 1, 7, 3, 7: the bent phase runs at most 1 + that times as fast as the ramp), so the bent sine stays under a quarter of the rate; the resonance's rise stops at log2(room) octaves.
- C: phase u32. The bend from 16-entry tables (`PD_T` start in Q16 cycles, `PD_S` slope in Q16): k = u >> 28, b = T[k] + S[k]·(u & 2^28 − 1) / 2^32 (one high multiply, no search), dcw·b as a u32 product (Q32, modulo a cycle), then `sin_turn`. The resonance ratio in Q16 from `exp2_q16`, its increment dt·m >> 16. A fast path (one bend wave, nothing at sync or pm) keeps the loop short. The reference reads the same bends from `PD_SEGS` in float. Golden kits `pd-bends` 0.15 %, `pd-alt` 0.4 %, `pd-reso` (an envelope on dcw, sync, pm) 2.4 % rel rms; the resonance's error is the restart landing one sample apart where the two engines' pitches differ by a hair.
- Cost on the rv32 model (`cpu-costs.json`), a block of 128 samples: about 10.6 k cycles for one bend wave (1.8 % of the FM-1's block with its parameter inputs), about 15 k with a second waveform or a resonance, 17 k with sync or pm patched, and 8.5 k more while the pitch moves every sample (vibrato: the increment's exp2 runs per sample, as on the Oscillator). Cassia 1 XL built a line from about 60 modules, about 450 k cycles per voice; a `pd` with its dcw input does it in 12 k to 25 k, which made Cassia 1, built on it, fit the FM-1; it plays two voices there ([D-348](ledger/patches-and-presets.md#D-348)).

## Granular

- `grain` (shared like the delay: one instance per patch, `SHARED_TYPES`): records `in` into a 1 s line (`GRAIN_SECONDS`; int16 Q13 on the device, `grain_line_t` = 88,392 B with the eight grain records, pool `gr_pool`, `ENG_NGRAIN` 1: one granular per patch). `density` grains per second start from a Q24 accumulator (the reference quantizes its increment to 2^-24 too, so both engines spawn on the same samples), a rising edge on `trig` starts one as well; at most `GRAIN_MAX` 8 play at once, a ninth is dropped. A grain reads `size` s (len samples) at rate 2^(pitch/12) from start = w − back, back = span + min(avail, floor(position·avail) + floor(rnd·spray·0.25 s)), span = floor(len·rate) + 1 (clamped to the line), avail = LEN − 1 − span, rnd from the LCG (seed 0x7f4a7c15; drawn even when no grain is free); so a grain never crosses the write head. Window sin²(πt/len) (C: `sin_turn` over half a turn, `winc` = 2^31/len), linear interpolation, the grains summed unnormalised; out = in·(1 − mix) + grains·mix. `freeze` stops the recording (w stays; the grains keep reading). With spray 0 and a frozen line every grain reads the same segment, so periodic content can cancel between grains: use spray. Golden kit `grain` (gated saw, LFO trig, pitch +7, spray 0.3): 0.5 % rel rms.

## Key-press trigger

Voicing and Part append `trig`: one sample at one when a key press reaches their allocator, then zero. The allocator's channel and note range still filter incoming keys. The pulse is independent of which pitch wins the priority rule. Releases produce no pulse. Several presses arriving in one block share its pulse. Idle parts retain the existing skip rule; running parts receive the pulse ([D-438](ledger/modules.md#D-438), Proposed).

Wanderer and Wanderer XL use legato pitch selection and subtract this pulse from the held gate. Their envelopes restart for a middle key press, but do not restart when an outer key is released. Existing gate outputs are unchanged in other patches.

## Math and logic

- Math's appended `xor` output applies exclusive OR to signed 16-bit audio samples. It first applies the gains and offset, multiplies by 32768, rounds down and clamps to −32768..32767. The result is divided by 32768. A zero mask preserves the quantized input. Elvira 2 XL uses this for BITMANGLER; its original mask sequence remains unverified ([D-437](ledger/modules.md#D-437), Proposed).
- `math`: a' = a·ka + off, b' = b·kb; outputs add, sub, mul, min, max, abs (of a'), cmp (1 while a' > b'). `logic`: inputs high at or above `thresh`; outputs and, or, xor, not (of a). Both stateless, per sample, Q16 in C. Golden kit `math-logic` (xor of two square LFOs gates an ADSR; max / abs of the math module on a VCA and a pitch).

## Selector (#351)

- `select` (Selector): a stepped switch of eight positions. k = clamp(floor(pos + cv·(count − 1) + ½), 1, count), cv = the `pos` input's first sample of the block (0..1 spans 1..count, so a 0..1 row read in N steps is one cable). `out` = in_k + v_k (with nothing patched in, a table of eight values); gate g_k is 1, the other seven 0. `fade` (0..100 ms) crossfades: every input's weight (Q16) moves towards 1 (chosen) or 0 by inc = floor(65536 / samples) per sample, samples = floor(fade_Q16 · 2891317 / 2³²) (2891317 = (44118 << 16) / 1000; `selectFadeInc`), the same integers in both engines; a change during a fade keeps fading from where the weights are. Settled, it copies one input; the gates are written only where cabled (C: `dummy_out`; the browser engine: the module context's `used`, the outputs with a cable or read by a probe or watch, which marks them from the next block).
- Eleven inputs (`pos`, in1..in8, p1, p2): `MAX_IN` became 11 and `node_t.conn` 16 bits wide (an input past the eighth has its bit). That is 3.3 KB more of the pool (`tools/pool_sizes.sh`: 128 instances × five more input pointers, 64 nodes × five more side-route masks).
- CPU: 2494 cycles alone (0.4 % of the block), 640 more per gate cabled, about 30 per sample more while fading. `apply_cv` skips the side-route loop when no input has one (bit-identical: `tools/engine_exact.sh`); with eleven inputs and eleven parameters it cost the Selector 1300 cycles a block.
- Golden kit `select` (three voices): a stepped LFO on a's pos with a 4 ms fade, a value table moved by p1 that transposes an oscillator with its gates on VCAs, an instant switch on a triangle.

## Envelope follower and compressor

- `dyn`: inputs `in`, `side`; outputs `out`, `env`. The detector is a one-pole peak follower of |side| (|in| when side is not connected) with the ADSR's rate formula (99 % in `attack` up, `release` down); it rides a little under the peak of a steady tone and ripples at the signal's frequency. Gain above `thresh` (dB): 2^(makeup − slope·(log2 env − log2 thresh)), slope = 1 − 1/ratio; below it only the makeup `gain` (dB). C: env Q24, rates Q30 (`env_rate`), dB → octaves by 1/6.0206 in Q16, one `log2_q16` + `exp2_q16` per sample while above the threshold (`exp2_q16` gives a plain integer: the Q16 / Q24 offsets are added to its argument). Golden kit `dyn` (gated saw into the compressor, its env output on a second VCA): 0.3 % rel rms.
- `esp` (Follower, patch format 46), after the Korg MS-20's External Signal Processor (its owner's manual, 1978, https://archive.org/details/JL11275: the ESP's controls SIGNAL LEVEL, LOW CUT FREQ, HIGH CUT FREQ, CV ADJUST, THRESHOLD LEVEL; its outputs amplifier, band pass, F-V CV, ENV and TRIG). Input `in`; outputs `amp` (in × `level`, held to ±16), `bp`, `pitch`, `env`, `trig`. `env`: a one-pole follower of |amp| (3 ms up, 80 ms down, the ADSR's rate formula); `trig` rises above `thresh` and falls below ¾ of it. `bp`: a one-pole high pass at `lowcut`, then a one-pole low pass at `highcut`. `pitch`: bp's period between rising crossings of +h after it went below −h (h = a quarter of bp's peak hold, which falls 1/512 per sample), each crossing placed between its two samples, as log2(f / C4) octaves plus `cvadj` semitones, gliding 1/64 of the way per sample. It holds the last pitch while bp's peak is under 1/256 (no pitch from silence) and drops a measurement after 4096 samples without a crossing. Nothing on `in`: it rests and costs a fill (the FM-1 has no audio input, #274, so on the FM-1 it hears only signals made in the patch). C: every state Q24, the one-poles' coefficients from `env_rate_q8` (the corner as the time 4.6 / 2πf), one 32-bit division per crossing and one `log2_q16` per period. Sallen 20 has one: `esp signal in` is its input, summed with its SIGNAL IN row (a Selector: OFF, VCO 1, white noise, the MG's triangle), its ESP ROUTE row (a Selector whose gates open a VCA or a Logic and per route: F-V into VCO 2's pitch, ENV into the VCA's cv, TRIG into the EGs' trigger Logic; [D-370](ledger/engine.md#D-370)) works on the FM-1, the TRIG route's loop through EG 1 and VCO 1 takes its block of delay on the route's own cable (its Logic is the assembly's first module, so `processingOrder` enters the loop there; golden kits `sallen-esp-2..4`), and the jacks the manual patches its outputs into are inputs too (VCO 1+2 CV IN, TRIGGER IN through a Logic or with the keyboard's gate, INITIAL GAIN). Golden kits `esp-pitch` (a played saw: pitch and env, 0.03 % rel rms) and `esp-follow` (the manual's patch: 0.14 %).

## Arpeggiator module, tempo and transport (#58, 2026-10-18; replaces the firmware arpeggiator)

- **Arpeggiator module** (`arp`, appended to `ALL`; `web/src/arpeggiator.ts` is the note logic, `engine.c` `arp_*` the same in C): keys in, keys out, between the Main module and a Voice allocator (`Main keys -> Arpeggiator keys -> allocator keys`). Params: mode (up, down, up-down without repeating the ends, random (LCG `seed * 1664525 + 1013904223`, index `(seed >> 16) % len`), as played), rate (1/4, 1/4T, 1/8, 1/8T, 1/16, 1/16T, 1/32 = 24, 16, 12, 8, 6, 4, 3 ticks of 24 ppqn), octaves 1..4, gate 0.1..1 (a share of the last step's length; the first step's length from the tempo), latch (a new chord after all keys were let go replaces the held one; turning latch off drops the keys already let go). Input `clk`: with a cable, one step per block with a rising edge there (the input as the last block left it); without, its own rate on the engine's clock. No p1 / p2 (`PIN_EXEMPT`), runs once (`SHARED_TYPES`), at most 2 per patch on the FM-1 (`ENG_MAX_ARPS`, `DEVICE.arps`).
- It runs at the start of every block, before the modules: block-quantized (a step lands on a block boundary, up to 2.9 ms late). Its notes go to the groups it plays (`group_on` / `group_off`); a part it lands on gets `retrig` (envelopes restart, also at gate 100 % where the next note follows in the same block). The keys reach the groups whose source is the keys and every arpeggiator.
- **Bypassed, fed by a track, into Drum maps (2026-10-23, [D-425](ledger/modules.md#D-425)):** a bypassed arpeggiator plays nothing of its own (`arp_block` / `arpBlock` skipped) and hands the keys it hears straight on: its groups and Drum maps take them as its own source's (`engine.c grp_src` / `dm_src`, `engine.ts effSrc` / `passesMain`: Main's keys, or the track's notes). It keeps the held keys, so switching it on arpeggiates what is held; a switch (bypass or its Toggle: `arp_switched` / `arpSwitched`) lets go of its groups' parts and its Drum maps' rows. An arpeggiator whose `keys` in is cabled from a Steps track's `keys` out plays that track's notes, not Main's keys (`node_t.ksrc` = 2 + the track's index; `ArpRun.feed`; `deviceView` keeps that cable in the device form). Its notes also go into the Drum maps it feeds (their ksrc = 2 + the arpeggiator's index; `deviceView` keeps the arpeggiator → Drum map cable so the compile pass keeps the arpeggiator). The factory patches use all three: Main → PATTERN → a bypassed arpeggiator on ARP → the voice ([D-336](ledger/patches-and-presets.md#D-336)). In the [grouped order](ledger/vocabulary.md#grouped-order) a device a track plays through an arpeggiator counts as driven by it, and a patch never opens on an arpeggiator (`homeDevice`, `pages_ui.c pages_frame`). The CPU estimate charges a Steps track Main's keys pass through `types.steps.thru` cycles per key (as many keys as the largest poly group has parts; `cpu-costs.ts thruCost`). ARP as the Toggle of Arpeggiators lights while they play ([D-231](ledger/device-ui.md#D-231): `engine.c eng_buttons_lit` for the LEDs, the bar's ARP ON / OFF and the EMU view, `buttons.ts arpLitInverted` for the dock); the engine's button bit stays "engaged = bypassed". `eng_keys_drummap` (the black keys on a Drum map) skips an arpeggiator a track feeds: the track, through it, decides.
- **Device form:** `poly.ts keySource` / `arpOf`; `deviceView` drops every keys cable, keeps the arpeggiator in the module list, gives an arpeggiated allocator a group even with one voice, and sets `DeviceGroup.src`. Binary format **23** (always written; `ENG_PATCH_COMPAT_VERSION` 23): the group record ends with its note source (`GROUP_REC` / `ENG_GROUP_REC` = 45 bytes: 0 the keys, else 1 + the arpeggiator's module index).
- **Continuous Arpeggiator rate:** the appended `rate` input is in hertz. Its previous block's average overrides the tempo-based note length. Positive values clamp to 0.02..80 Hz; zero or negative values pause and release the sounding note. A cable in `clk` takes precedence. Both engines accumulate unsigned 32-bit turns with the same quantized increment, so timing stays within one block without accumulating block-rounding error. Gate length follows the current period. The CPU probe counts note scheduling as well as the module's signal output ([D-439](ledger/modules.md#D-439), Proposed).
- **Tempo and clock:** Main parameter `tempo` (20..300 bpm, whole bpm, default 120). The engine's clock (`Engine.ticks`, `E.ticks`) always runs: per block `acc += n x bpm x 24`, a tick per `60 x sr`; while MIDI clock comes in (`clockExternal` / `eng_clock_external`; the worklet and `midi_drain` turn it off after 0.5 s without a tick) its ticks replace the tempo. **Transport:** `Engine.transport` / `eng_transport` (PLAY on the FM-1, the deck's Play and Space in the browser, MIDI Start / Continue / Stop, protocol TRANSPORT 0x25 with INFO feature bit 1); a new Main output `run` is high while it runs; the Main `clock` output pulses (half a block per block that saw a tick) only while it runs. Arpeggiators step whether or not it runs.
- **MIDI clock out** (`web/src/clock-out.ts`, FM-1 & MIDI > MIDI clock out, [D-466](ledger/link-and-midi.md#D-466)): while on, the ticked Web MIDI outputs get clock (0xF8, 24 a quarter note at Main's `tempo`, read at every clock) all the time, and Start / Stop (0xFA / 0xFC) when the transport switches. Each clock is sent `LOOKAHEAD` (300 ms) ahead with its own timestamp; the timer is a worker's (`clock-tick.ts`, 25 ms) so a background tab keeps its pace, and a timer over 1 s late restarts the clock from now. The browser engine keeps its own tempo clock: it does not follow the clock it sends.
- **Old patches:** `Patch.arp` (the firmware arpeggiator's settings) is dropped by `validatePatch`; its bpm becomes the Main module's tempo when the patch had none. `arp.ts`, `arp.c`, `arp_ui.c`, the arp pages (ARP / SEQ / LFO buttons now unused, for #60), the ARP command 0x24, `tools/arp_test.sh` and the dock's arpeggiator panel are gone; the dock's clock column has the clock and run jacks and the tempo; Play (`#arp-btn`, the tutorial target) is PLAY in the dock's button block since #113. The saved-state record keeps its arp bytes as zeros.
- Golden kits `arp-updown-poly`, `arp-random-latch`, `arp-clk-played`, `main-clock-run` (events `run` / `stop` in `.ev`, `host_test` calls `eng_transport`).

## Macro ranges

- Model: `ModuleInst.range` = `{ p1?: { [param]: [lo, hi] }, p2?: ... }`, ends 0..1 in `paramUnit` space (octaves for a log parameter, no slider bend; `paramValue` is the inverse: the same pair the morph uses). `fixMatrix` keeps a range only on parameters the pin controls (`map`) and clamps the ends; `rangeOf(m, pin, name)`.
- Engines: in applyCv / apply_cv a pin with a range on the parameter sets the base to `paramValue(lo + clamp(v, 0, 1) × (hi − lo))` with v = block mean × attenuverter (replacing the slider's value and the morph), the other pin adds as before (`modulate`, which for a log parameter adds in the bent unit space exactly as it always did, so patches without ranges are bit-identical). C: `range_t E.ranges[ENG_MAX_RANGES]` (48 per voice: module, pin, parameter, lo, hi as u8) and `node_t.ranged[2]` bit masks so the table is only scanned for a ranged destination; `morph_value` maps the u8 ends (× 257 → Q16).
- Binary format 15: header flag bit 1 = a macro range section after the morph B set: u8 count, then 5 bytes per range (module index, pin, parameter index, lo, hi as 0..255). The section is last, so a live edit on the device (`m1_patch_range`: update, append, or remove by moving the last entry into the hole) never shifts the records. Protocol RANGE 0x23 (module, pin, param, on, lo, hi); `eng_set_range` / `eng_range`.
- LCD: `module_row_b` draws a bracket (ticks at both ends, a line between them) over the bar of a knob row whose parameter has a range on p1 or p2.
- Golden kit `macro` (a triangle LFO into the filter's and the ADSR's p1 with ranges in octaves, the ends of the decay swapped; K2 into the oscillator's pulse width): 1.6 % rel rms.

## Patch morphing

- Model: `ModuleInst.paramsB` (the B side's parameters per module, never on the Main module), `Patch.morphName` (display). `sameStructure` (same module types in order, same cables by module index), `setMorphTarget` / `clearMorph` / `hasMorph`, `morphValue(pd, a, b, t)` (choices and toggles snap at 0.5; log parameters interpolate in octaves without the slider's bend; the rest linearly). The Main module gained the parameter `morph` (0..1) and the control input `morph`.
- Engines: the morph position of a block is the Main's `morph` parameter plus the block mean of its morph input, which holds what the input summed in the previous block (one block late, so the LFO can be anywhere in the processing order), clamped to 0..1 (`Engine.morphPosition`, `morph_position` in engine.c). applyCv / apply_cv start from the morphed base instead of the parameter when the patch has a B side and the position is above 0; the modulation then adds as before. The firmware keeps the B side as unit positions (`node_t.parb`, u16 per parameter, octaves for a log parameter: `morph_unit` / `morph_value`), 24 B per node. A cable into the Main's input never makes the Main per voice (`voiceSplit`, and in C the panel already has nv instances); T_GRAIN was missing from the C shared list and is there now.

## Reverb (FDN)

- `reverb` is an eight-line feedback delay network: line lengths 331 439 547 661 773 881 991 1117 samples (primes, 7.5..25 ms at 44118 Hz; the TS engine scales them with the sample rate), Householder feedback f_k = t_k − Σt/4 (lossless mixing, so the decay is set by the per-line gains alone), in every line a one-pole damping filter (coefficient damp × 0.8) and a gain g_k = 10^(−3 L_k / (T·sr)) so that every line loses 60 dB in T = 0.2 × 2^(5·size) s (0.2 .. 6.4 s). Input: pre-delay (0..40 ms, `pre`), two diffusion allpasses (223, 347 samples, g 0.5), × 0.125 into every line; wet = Σ raw line outputs × 0.5. Lines 0 and 1 are read with a fractional, linearly interpolated delay that swings by `mod` × 6 samples (sine at 0.5 and 0.83 Hz): the chorusing that keeps fixed lines from ringing. Measured in the test: a sustained noise of 0.5 rms gives a wet level of 0.13 (size 0) .. 0.29 (size 1); the tail of size 0.5 falls 53 dB/s. Memory: 8074 int16 samples = 16 KB per instance (`RV_LEN`; was 12 KB): one reverb per patch. C: Q13 lines as before, T and the gains through `exp2_q16`, the modulation through `sin_turn`; golden kit `reverb` 0.1 % rel rms (the C and TS modulators agree to a fraction of a sample over the whole tail).

## Oversampling toggle (shaper, digitizer) and sequencer glide / gate

- `shape` and `crush` have an `os` toggle (patch format 13: new parameters). With it the module runs at 2x: the FM oscillator's polyphase half-band (the same four allpass sections, Q16 coefficients `HB` / `HB_A`) is used as the interpolator (even sub-sample = path 0, odd = path 1, no gain change: the zero-stuffed signal's half-band has gain 2) and again as the decimator, path 1 fed the odd sub-sample of the previous frame as in the oscillator (`os2` in modules.ts; `os_up0` / `os_up1` / `os_down` in engine.c, 17 words of state). Measured in the test: a 5 kHz sine hard-clipped at drive 4: the 5th and 7th harmonics, which fold to 23 and 13 kHz at 48 kHz, drop by 11..12 dB with `os` (what is left is the folding of still higher harmonics at the doubled rate); the fundamental and the 3rd harmonic are unchanged, the rms is 9 % lower (the energy above 22 kHz is gone rather than folded). The digitizer's `rate` keeps counting input samples (the counter runs at 2 x rate). Golden kit `os-shape-crush` (saw into a hard clip into 5 bits / rate 3, both oversampled): 1.2 % rel rms.
- `seq` parameters `glide` and `gate` (fractions, 0..1): the clock period is measured between the last two rising edges (`since` / `period`, nothing until two edges were seen), `glide` is a one-pole on `out` reaching 99 % in glide × period (Q24 state, `env_rate_q8`; 0 = the step itself, bit-exact as before), `gate` holds the gate output for round(gate × period) samples after an edge that lands on a non-rest step (1 = legato; 0 = the clock's own width as before). MAX_PAR is 12. Golden kit `seq-glide`: 0.8 % rel rms.

## Filter: notch, peak, allpass outputs

- `filter` outputs `notch`, `peak`, `ap` appended after `mix` (positions are append-only, so the binary patch format is unchanged). From stage 1's values (v0 = in, v1 = bp, v2 = lp12, k = 2 − 1.98·res): notch = v0 − k·v1 (= lp12 + hp), peak = v2 − hp (= lp12 − hp: unity far from the cutoff, 2/k at it), allpass = v0 − 2k·v1 (= notch − k·bp, |H| = 1). The C version computes them only when one of the three outputs has a cable (`dummy_out` check once per block). Golden kit `filter-notch` (saw, sine LFO on cv, the three outputs mixed): 0.2 % rel rms.
- `filter` output `hp6` (patch format 45), appended after `ap`: hp + 2·bp = (s² + 2s) / (s² + k·s + 1), the high pass of the Korg MS-20's filter as T. E. Stinchcombe derives it ("A Study of the Korg MS10 & MS20 Filters", section 7): 6 dB per octave below the cutoff, √5 / k at it, unity above. The C version computes it in the same branch as notch / peak / allpass. Sallen 20 takes its high pass from it. Golden kits `filter-hp6-0.2` and `filter-hp6-0.95`.
- `filter` parameter `osc` (patch format 47, appended, off by default): self-oscillation, as the Korg MS-20's filters at full PEAK. On, from `res` 0.85 (`FILTER_OSC_FROM`) up, stage 1's damping is k = 2 − 1.98·res − 1.19·d + 5.6·d·b² (d = res − 0.85, b = the band-pass state ic1 held to ±2): below 0 from about res 0.95, it grows with the level, so the filter rings a bounded, nearly sine tone at the cutoff (a Van der Pol oscillator: about 0.5 peak on lp12 at res 1, at any cutoff; the pitch within 1 % of the cutoff up to a few kHz). A filter at rest starts from ic1 = 1/1024. The C version (`filter_run` with osc a constant at each call, as `ladder_run`) solves stage 1 per sample there (`svf_stage`, one division); off, or below 0.85, the filter is the same code as before. Sallen 20 turns it on in both filters ([D-371](ledger/engine.md#D-371)). Golden kits `filter-osc-self` (no input, res 1) and `filter-osc-driven` (a saw, res 0.97, the cutoff swept).

## Ladder filter

- `ladder`: four TPT one-poles (y = G(x − s) + s, s' = y + v with v = G(x − s); G = g/(1+g), g = tan(πfc/sr)) in a loop with k = 4·res. Zero-delay feedback solved linearly per sample: y4 = (G⁴x + S)·F with S = (G³s₁ + G²s₂ + Gs₃ + s₄)(1 − G) and F = 1/(1 + kG⁴); the loop input is then u = sat(drive·x − k·y4) and runs through the stages (the saturator is inside the loop, so at res 1 the self-oscillation limits itself). sat(v) = v − v³/6.75 for |v| ≤ 1.5, ±1 beyond (slope 1 at 0, peak 1). Outputs lp24 (stage 4) and lp12 (stage 2). Parameters cutoff (log, 20..4000 Hz), res, drive (1..8, log), cvamt, track. The coefficients are computed once per block from the block mean of `cv` (× cvamt, + key tracking), unlike the SVF's per-sample update: one `recip24` per block instead of one per sample. No resonance compensation (the passband drops with res, as on the original). C: G, G²..G⁴, F in Q24, states Q20, products rounded; the saturator bounds the states so they need no clamps. Golden kit `ladder` (saw, LFO on cv, res 0.85, drive 3): 0.12 % rel rms.

## Bypass (module on / off)

Every module except Main and Output has a bypass switch, the way a device in a DAW rack can be turned off. A bypassed module does not run (its state is kept, so it resumes where it stopped when turned on again) and its outputs carry its **through input**: `ModuleDef.thru`, by default the input called `in` (filter, ladder, delay, reverb, chorus, shaper, digitizer, phaser, vowel, glide, comb, modal, shifter, compressor, granular, S&H, quantizer); the mixer passes `in1`, the crossfade `a`, the pan copies `in` to both `l` and `r`. A module without a through input (oscillators, LFOs, envelopes, noise, sequencer, string, math, logic, pulse, clock divider) is muted: silence on every output. Input sums still run, so a bypassed module inside a feedback loop keeps the graph consistent.

- Model: `ModuleInst.bypass` (patch.ts, dropped on Main / Output by `validatePatch`), `thruInput(def)`. Binary format 12: bit 7 of a record's type byte (the record size is unchanged); `ENG_PATCH_VERSION` 12.
- Engines: `Engine.run` copies or clears the outputs (`Engine.setBypass` for the live switch, worklet message `bypass`); engine.c `m_bypass` instead of `process()` (`node_t.bypass`, `eng_set_bypass` / `eng_bypass`, `def_t.thru` from export-defs).
- Protocol: `22 BYPASS module u8, on u8` (protocol.ts, proto.c `m1_patch_bypass` keeps the stored copy in step so SAVE / STORE keep it).
- Editor: the ⏻ button in the card header (the body dims, undo works); `EditorEvents.onBypass`. An assembly's ⏻ bypasses its members (see **Assemblies** below).
- FM-1: a patch button of the Toggle kind bypasses its module or assembly ([D-213](ledger/device-ui.md#D-213)); FX is the SEQ page's accent key and SEL held the roll's pen ([D-223](ledger/device-ui.md#D-223)).

## Parameter ranges and steps (audit)

- The editor's logarithmic sliders rounded their value to a whole number (`Math.round` after `fromUnit`), so a glide time, envelope rate, chorus or phaser rate, drive, grain size or decay could only take 0, 1, 2 ... They now snap to the parameter's `step` (`snapTo` in editor.ts); the LCD knobs were not affected (`eng_step_param` works in octave units).
- Filter and Ladder `cutoff` open to 16 kHz (was 4 kHz; the tan table allows 0.45 of the sample rate). The modulation range is 9.6 octaves now instead of 7.6, so a parameter input on the cutoff moves it a bit further per unit; the Pluck preset's K1 start was recomputed.
- LFO `rate` (0.02..40 Hz) and the ADSR's `a`, `d`, `r` are logarithmic like the Env L/R rates and Glide: the slider and the knobs give the short times room, modulation moves them in ratios.
- The Delay's `time` goes 1..520 ms, the length of its line (`DELAY_TIME_MIN/MAX` in modules.ts; it went to 1000 and was clamped); the synced note lengths are spread over that range (stored synced values pick a different length than before).
- **The browser's long Delay** ([D-426](ledger/modules.md#D-426)): in the browser the Delay's `time` reaches 1600 ms (`DELAY_TIME_BROWSER`; its line holds 1.6 s), the FM-1's stays 1..520 ms. It is a browser-only stretch of the parameter (`ParamDef.browserMax`): `max` stays 520, so the knobs, modulation, macro ranges, the synced note lengths and `defs.h` keep the FM-1's range, and the card's slider runs to 1600. A time within 520 ms plays as on the FM-1, its line's length bounding a synced note length too; a time past it uses the longer line, synced it picks the longest note length (1/1). A patch with a time past 520 ms, on either morph side, uses a browser-only ability (`browserOnly` in patchbin.ts: "Delay over 520 ms: browser only"), so `deviceBudget` counts it over the FM-1 budget (a `browser` line in `over`): it is a sandbox patch, `encodePatch` refuses it, and the budget breakdown lists the reason. Moving the slider across 520 ms re-checks the budget before Live would send the value (main.ts `onParam`).
- **Range extensions as new rows** (#351, [D-429](ledger/modules.md#D-429)): an existing parameter's `min` / `max` never widens, because pins, macro ranges and the knobs map onto that range, so a wider one would change old patches. A new row, whose default plays as before, scales or replaces the value inside the module (both engines, the FM-1 too; no new memory):
  - ADSR `long`: `d` and `r` times `ADSR_LONG` (2.4; C `ADSR_LONG_Q16`), up to 12 s and 19.2 s. The card shows the stretched time (`altText`); the LCD shows the row's own value. The C release now steps at least one Q30 unit per sample: past about 11 s `v · ar` rounds to 0 above the end level and the envelope would never end (old times never get there, so old patches stay bit-identical).
  - LFO `phase` (0..360 degrees): added to the phase where the wave is read, so a reset or a clock restart starts there. `dir` back: the wave read at `off − phase`, done as −w(phase − off) for sine, saw and square (odd waves) and w(phase − off) for the triangle, so the poly-BLEP keeps its sign. `range`: free rate × 1, / 25 or × 2 (`LFO_RANGE_K`; C: `(rate << 16) / (25 · sr)` for slow, `hz_turns << 1` for fast). The `rate` row shows the rate the LFO runs at, the value times its range's factor (`lfoRateText` through `altText`; the FM-1's `stretched` in pages_ui.c), while its knob keeps the row's own 0.02..40 ([D-372](ledger/engine.md#D-372)). Io 4's LFO RATE is the fast range: 0.04..80 Hz, the Jupiter-4's top. `mult` (/8 .. x8, `LFO_MULTS`): the synced length × num / den. Ticks per cycle are then fractional (a 1/16 triplet x8 is half a tick), so `lfoSyncCycle` works in per8 = 8 × ticks per cycle (a whole number for every length) and snaps every `snap` = per8 / gcd(per8, 8) ticks, where `cycles` = 8 / gcd(per8, 8) cycles end; the clocked phase wraps freely `cycles − 1` times and waits at the end of the last. A whole-tick length is snap = ticks, cycles = 1: the old rule, bit-identical.
  - Delay `note` (synced): one of `DELAY_NOTES` (1/32, 1/2T, 1/2., 1/1T, 1/1.) in place of the time knob's length; the line still caps it (520 ms on the FM-1, half with ping-pong). `swell`: fb × 198 / 95 (0.95 reads 1.98) and every write into the line through `delayClip` (x − 4/27 x³, flat at ±1 from 1.5; C `dly_soft`), so a loop gain past 1 settles near full level. C runs the swell in a loop of its own, so the plain loops are unchanged.
  - Reverb `freeze`: every line gain 1, damping 0, nothing into the lines; the Householder matrix is lossless, so the tail holds (C: the lines keep their Q13 rounding; the modulated taps' interpolation slowly softens the highs).
  - Pulse `inf`: the countdown stops while it is on (a new trigger reloads it); switched off, the window ends `time` after the last trigger.

**Assemblies.** The ⏻ on an assembly card or frame (`bypassAssembly` in assembly.ts) bypasses every member, nested ones too, and remembers in `AssemblyInst.kept` which members were already off on their own; switching the group back on restores exactly that. A nested group's own switch is superseded while the parent is off. `toDef` writes the members' own switches into a saved definition, not the group's. Editor only, like the rest of the overlay.

## Fixed input links and additional routes

A parameter whose definition names a dedicated input (`ParamDef.input`: VCA gain from `cv`, filter and ladder cutoff from `cv`, filter and Main `morph`, shift `cv`, pan and crossfade `pos`, vowel) is **permanently** fed by it: that wiring is what makes the module the instrument it is, so the editor draws the route inside the card greyed out (`.cable.alias.fixed`) and offers no way to cut it. Dropping a cable on such a parameter's slider thumb plugs it into the dedicated input (`connectParameter`). An unplugged dedicated input reads silence in both engines; for the VCA that means **a VCA with nothing at its cv is closed** (as on a modular; before 2026-10-14 it passed at full gain), so a level trim needs a Constant into cv, or the Output's / a mixer's level. `ModuleInst.disabledInputs` (format 17, flag bit 2) was the switch for these links; `validatePatch` drops it, so an older patch gets its built-in routing back, and the encoder never writes the flag. The firmware still reads the flag for binaries stored by older editors (untested: no kit exercises it any more).

`ModuleInst.inputMap` adds destinations to any non-p1/p2 side input: these are the user's own internal routes (coloured, click to disconnect, drag a side jack to a thumb to add one). Each source's block mean adds a normalized parameter-range offset (octaves for a logarithmic parameter), alongside the p1/p2 modulation. A dedicated input is excluded from the map for its own parameter (no double modulation). Patch and assembly validation remove invalid and duplicate destinations.

Binary format 18 adds header flag bit 3: a count byte followed by module index, input index and a u16 parameter mask per routed input, after the (now never written) disabled-input masks and before macro ranges. The firmware accepts 16–18. The encoder uses 18 only for additional routes and 16 otherwise, preserving unchanged patches for older firmware. Golden kits `fixed-links` (every dedicated link at once) and `side-input-fanout` compare the browser and C engines.

## Voicing (issue #22; Main's voicing moved to poly assemblies in format 20)

Serum 2's Voicing panel in this modular's terms, plus the parts of an analog polysynth that drifted out of spec.

- **Legato, priority, flaws** are settings of a poly assembly (see Polyphony); a mono voice with them is a poly assembly of one part. `auto` is legato with one part and a restart for a taken-over part; `off` restarts the envelopes on every change of key while the gate is up (one part: also when a release falls back to a held key); `on` never does.
- **Part outputs** `legato` and `jump`. Recipes: Serum's ALWAYS = a plain `glide`; legato-only portamento = Part `legato` into the glide's `time` thumb with a depth (or a macro range); SCALED = `jump` → math `abs` → glide time, or simply the glide's `lin` curve (constant rate, so a bigger step takes longer). Per-part detune / cutoff / envelope spread: a fixed **Random** into the destination with a small depth; slow pitch wander: a walking Random into an oscillator's `fine`.
- **Oscillator** `blend` (0..1, default 0.5): copy weights centre 1 − b, others b, normalised (`blendWeights`; the centre is the middle copy, or the two middle ones; with one or two copies all are equal), so 0.5 is the plain average, 0 the centre copy alone, 1 the detuned copies alone. `stack` (off / +oct / +5th / +oct+5th / −oct): the copies cycle through the intervals (copy j at `STACKS[k][j % n]`), and the copy count is at least the number of intervals (unison 1 with +oct plays two copies; the cap of 5 copies stays: each copy is a full oscillator). The level stays at `level` because the weights sum to 1. Blend, stack and unison are plain-path only. (The oscillator's own `drift` is gone: a Random drifts a whole part, not each unison copy.)
- **Glide** `curve` (exp / lin): exp is the one-pole (99 % of any step in `time`); lin moves at one unit per `time` (C: Q24 step `2^40 / (time_q16 · sr)`).
- **Factory assemblies**: `mono lead` (one part, the Part's legato into the glide), `supersaw stack` (four parts panned by index), `drift poly` (was `analog voice`, briefly `basic mono`: four parts, walking Randoms on the oscillators' fine tune, a fixed one on cutoff and decay), `basic poly` (was `poly voice`: the plainest four-part voice). Tutorial chapter 12 "Voicing" (unpublished) walks through all of it. Tests: `web/src/voicing.test.ts`, `web/src/poly.test.ts`.

## The bank: 64 slots, power-safe, SAVE writes the slot (#61 #62 #74, 2026-10-18; replaces the saved-state blob and patchstore.c)

- `firmware/src/slotstore.c`: 64 patch slots (`M1_SLOTS`) plus one settings record (id `SL_SETTINGS` = 64), log-structured over 66 sectors (0x97000, 0x98000 = the old patch store, and 0xA0000..0xDFFFF; all inside Felucca's data window, never erased by the loader). One record per sector: header (magic "M1S2", id, sequence number, length, CRC-16, name; written last = the commit) + data from +256 (up to `M1_PATCH_MAX` 3840 B). A write takes a sector without a live record (round robin), erases it, programs data then header, verifies, and only then erases the replaced record's sector; at boot (`sl_scan`) the newest valid record of each id wins and older copies are erased. 65 live records in 66 sectors: one is always free. 32-slot bank records ("M1SL" at 0xA0000 + n x 4 KiB) are read as slot n with sequence 0.
- The bank is the device's only patch list: PRESET steps the occupied slots, program change n = slot n (empty: ignored), the editor's SLOT commands address 0..63 (`SLOTS` 64 in protocol.ts). People see slots numbered 01..64 (`slotLabel`), so program change 0 loads slot 01. The first boot (an empty store) and MENU > SYSTEM > FACTORY RESET (`sl_clear_all`, ~3 s) write the factory patches (presets.h) into slots 0.. (`factory_bank`). A slot that does not load, or none at all, plays `FALLBACK_PATCH`.
- SAVE (and the editor's STORE) writes the running patch, edits included, into the slot it came from (`cur_preset`) under that slot's name, and the settings record (12 bytes: version, slot, octave, LED mode, knob accel, CPU in the bar, clock in, program change, MIDI channel, level, mute, selected module). The next boot opens the slot the settings record names. Choosing a patch does not write the flash (an erase stops the audio for a moment), so the boot opens the slot last saved. Edits since the load show as ` *` after the name (`m1_edited` in proto.c, set by the live edit writers, cleared by `m1_set_current` and SAVE).
- Gone: `patchstore.c`, the state blob and its versions, `state_pack`, `ps_*`; old stored states are not read.

- **Notes (#133, format 31, `web/src/track.ts`):** `ModuleInst.notes` = `StepNote[]` (`at` start step 0..63, `len` steps, `note` MIDI, `vel` 1..127, `chance` 5..100 % in steps of 5, absent = 100), sorted by step then note, one per step and key (`fixNotes`), at most `TRACK_NOTES_MAX` 128 per track (per pattern) and `DEVICE.notes` 1536 per patch, every pattern counted (the FM-1's pool, `ENG_MAX_NOTES`). - Playing (`modules.ts steps`, `engine.c m_steps`, the same): on step k every note sounding with steps left goes on (two steps more at most, so a stopped clock lets it end), then the notes starting on k sound unless muted or their chance says no (`notePlays` / `steps_plays`: `hash32(seed ^ loop·0x9e3779b9 ^ (k+1)·0x85ebca6b ^ j·0xc2b2ae35) % 100 < chance`, j = the note's place among the step's notes, so note 0 hashes as the old step did). A note lasts min(len, track len − k) steps, `gate` of its last step; at most `TRACK_POLY` 8 sound at once (the oldest ends), a note on a key that sounds ends it first. `trig` is up while any note sounds (one low sample when a note starts over a sounding one), `pitch` (octaves from C4, plus `transpose`) and `vel` (v / 127) hold the last note that started (the highest of a chord). **keys out:** every note on / off, transposed by whole semitones (`floor((q16(transpose)·12 + 32768) / 65536)`), like Main's keys: a Voice allocator fed by it gets a group whose note source is the Steps module (`DeviceGroup.src`, the group record's source byte; poly.ts `keySource`). - Clock: with nothing in `clk` the first step comes when the transport starts, then one step per `rate` ticks of the engine's clock (tempo or MIDI clock), each on the sample its tick falls on (the engines report the block's tick offset, count and samples per tick: `Voice.tick` / `ticks` / `tickLen`, `E.tick_off` / `tick_n` / `tick_len`; MIDI clock ticks fall on the block's first sample, their length is measured). ## MIDI in and out (#64, 2026-10-18)

- In (USB and TRS): one channel (MENU > MIDI > MIDI CHANNEL, omni by default): notes (but see the key range below), pitch bend, CC 1 (mod), aftertouch, program change n = bank slot n, counted from 0 (program change 0 = slot 01; an empty slot, or while the editor's Live is on: ignored), CC 16..19 = K1..K4 (the rows of the page in focus), CC 22 = morph, CC 80..86 = presses (64 and up) and releases of the patch buttons FX..ARP, CC 123 = all notes off; clock, Start / Continue / Stop (MENU > CLOCK IN).
- Out (USB only; MENU > MIDI > MIDI OUT, on by default; TRS has no out): every panel control, the "MIDI out map" below (#115). What came in is not sent out again. Not verified: USB is not emulated.

### MIDI out map (#115, 2026-10-19)

Every control goes out as it is touched, raw, whatever it does on the device at that moment (a host can mirror or replay
the panel); on the MIDI channel (omni: channel 1). Sent from the panel core (`panel.c` `BTN_CC`, `ENC_CC`, `panel_master`),
checked by `tools/panel_test.sh`.

| Control | Message |
|---|---|
| keys | note on (velocity 100) / note off, at the octave; while the keys reach a Drum map a black key sends its row's note, a white key nothing ([D-525](ledger/steps.md#D-525)) |
| K1..K4 | CC 16..19, absolute: the bound row's position (only on a device page, when the knob moves a row) |
| SELECT, ALGO, PRESET | CC 20, 21, 23, relative two's complement (1..63 = up by n, 127..65 = down by 128 - n) |
| MASTER | CC 7, absolute (the pot's 10 bits >> 3; changes under 6 / 1024 dropped) |
| FX SCL ENV LFO EDIT GLO ARP | CC 80..86 |
| HOME SAVE SEQ REC PLAY | CC 87, 88, 89, 90, 91 |
| OCT- OCT+ | CC 92, 93 |
| PLAY starting / stopping the transport | also Start 0xFA / Stop 0xFC (not when PLAY held + PRESET set the tempo) |

Buttons send 127 on the press and 0 on the release, a switching patch button too (the editor and the FM-1 itself take
CC 80..86 coming in the same way, so a switch is one press). CC 22 (morph) is in only.

### Following the FM-1's panel, any firmware (#120, 2026-10-19)

- The page reads a connected FM-1 through plain MIDI only (`web/src/mirror.ts` `Fm1Mirror`: its own listener on the
  port; the firmware from M-VAVE's identity handshake, `fm1-profiles.ts` `firmwareOf`: FM-1_7XY ours, FM-1_9XY Felucca
  or Sloop, FM-1_0XX / 8XX M-VAVE; Baud Girl by hand). A profile per firmware (`PROFILES`) turns its messages into panel
  inputs: Matryoshka the map above; M-VAVE the keys; Felucca / Sloop the keys, CC 1 (Felucca's MODW mode) as the
  modulation wheel, Start / Stop; Baud Girl the keys and K1..K4 as CC 74 / 71 / 73 / 72.
- main.ts `mirrorInput`: buttons and encoders go through Matryoshka's panel logic (the FM-1 tab's WebAssembly copy,
  `Fm1View.drive`, loaded even while the tab is hidden; its focus / page events move the editor as the emulator's do)
  and the patch buttons also through `Editor.pressButton`; K1..K4 positions through `Editor.turnKnob`; keys, the
  modulation wheel, MASTER and the transport to the page. Nothing is sent back to the FM-1 (`fromDevice`). PRESET is
  not followed while Live is on (the FM-1 then plays the editor's patch; its slots are its own).
- The Emulator view shows a "Mirroring your FM-1" marker over the panel (its tooltip names the firmware) and greys the
  controls that firmware does not report (`Fm1View.following`).
- The FM-1's CC on the Live link are not used by the page. A knob's value arrives as its row's 7-bit position (CC 16..19),
  not the exact value, and turns K1..K4 of the editor's page in focus; except under Live with the FM-1 on the editor's
  patch (`exactKnobs` in main.ts, #185): then PARAM_NOW (module, parameter, value) moves the parameter and FOCUS_NOW the
  page (the editor and the mirror's panel copy), so a turn cannot land on another row when the two disagree on the page.
- **LIVE** (#185, protocol 0x2C, feature bit 6): every 2 s while Live is on (`LIVE_MS`) the editor tells the FM-1; paused
  (the patch over the budget) it is sandbox mode (below); until 5 s
  after the last (`LIVE_HOLD_MS`, main.c `editor_live`) PRESET and program change load no slot (`EDITOR LIVE: NO PRESET`),
  so the FM-1 cannot leave the editor's patch under it. An FM-1 without LIVE (1.0.0) still can: its SLOT_NOW then ends
  `exactKnobs` until the next upload.
- Connect FM-1 (it answers HELLO, so it runs Matryoshka) also starts following it; FM-1 & MIDI > Follow the FM-1 does
  it for any firmware, with a firmware list (detect, or by hand).

### Sandbox mode: the FM-1 as a sandbox patch's controller (2026-10-24)

Rows: [D-467](ledger/link-and-midi.md#D-467) (the mode), [D-468](ledger/link-and-midi.md#D-468) (the message, INFO),
[D-232](ledger/device-ui.md#D-232) (the FM-1's screen and controls). Not checked on a device.

- **When.** The editor's patch is over the FM-1's budget (`deviceBudget(p).fits === false`) while it is connected with
  Live on: `liveSync.sandbox` (device.ts). LIVE keeps its paused flag (byte 1). With Live off, the sync line's Sync
  (`syncLine`: "Sandbox patch, not synced") starts it, and so does the connect offer's Sync
  ([D-460](ledger/link-and-midi.md#D-460)). It ends when the patch fits (Live then uploads as before), when Live is
  turned off, or, on the FM-1, 5 s after the last LIVE (`SB_HOLD_MS`, the same as `LIVE_HOLD_MS`).
- **Editor** (main.ts `sandboxCheck`, called by `syncChip` on every link, Live and budget change): entering it starts
  following the FM-1's panel (the mirror, `followFm1('matryoshka')`) unless it already follows, and leaving it stops what
  it started (a user's Stop following wins). One transport: entering it runs both the editor's and the FM-1's if
  either ran (`liveSync.sandboxRuns`; `DeviceLink.running` is the FM-1's last MIDI Start / Stop or TRANSPORT), and the
  editor's PLAY and Space send TRANSPORT in sandbox mode as under Live (`liveSync.transports`), so a sequence the FM-1 was
  playing goes on in the browser and the FM-1's PLAY stays in step. Its knobs come as CC 16..19 positions (`Editor.turnKnob`); SELECT / ALGO move
  the editor's own focus (`sandboxStep`, wrapping as the FM-1 does: the firmware UI's WebAssembly copy may have refused a
  patch this big); the buttons go through that copy as before, the keys to the browser engine; PRESET is not followed. Every
  `SANDBOX_MS` (80 ms) `sandboxSend` builds the page in focus (`sandbox.ts` `sandboxPage`: the device, its page as the
  FM-1's chips title it, the page's place, four rows with the value and unit as the dock shows them, the position 0..1 and
  the choice count) and sends it when `sandboxKey` differs from the last one sent (a fresh sandbox mode or reconnect sends
  it again). The FM-1 chip: `FM-1 · SANDBOX CONTROLLER` in gold (`sandboxChip`); with MENU > MIDI OUT reported off,
  "turn on MIDI OUT (GLO, K3) to control the sandbox"; with firmware older than 1.3 (no feature bit 8) its hover asks for
  the update (that FM-1 keeps its sound and shows `EDITOR PATCH TOO BIG`, and the CC 16..19 it sends are its own rows'
  positions, so a knob jumps the editor's row as on any Live-off follow).
- **Protocol.** SANDBOX 0x31 (host to device, no reply, feature bit 8; `protocol.ts` `sandboxFrame` / `parseSandbox`,
  `firmware/src/sandbox_msg.h` `sb_parse`): rows u8 (bit k: row k), index u8, count u8, patch 20, device 12, page 16, then
  four rows of label 12, value 10, unit 6, position u8 (0..255), steps u8 (0 continuous, n choices); names zero padded
  ASCII (`fm1Ascii`: a minus sign becomes `-`). 171 bytes, 202 on the wire. INFO grows a seventh byte (feature bits
  8..15; `M1_FEATURES2` = 1: bit 8) and flag bit 2 = MENU > MIDI OUT on (`Info.midiOut`, null without bit 8); the FM-1
  sends INFO unasked after a LIVE when MIDI OUT changed since it last told (live.c `live_mout_told`), and `DeviceLink`
  takes an unasked INFO as an `info` event. Tests: `protocol.test.ts`, proto_test (`tools/golden.sh` feeds it the frame
  golden.ts writes, `proto-sandbox.syx`).
- **Firmware** (`sandbox_ui.c`, live.c, panel.c, audio.c). `m1_live(1)` turns sandbox mode on (`sb_on`); audio.c's
  `snd_muted` zeroes the output (the FM-1's own patch keeps running, unheard). Entering it brings page 0 up
  (`sb_home_due`, panel.c `panel_status`) from any screen but the menu and GLO, so the SEQ page does not stay up. Page 0 draws `sandbox_draw` instead of the
  device page (ui.c `view_draw`, `header_draw`): the gold band with SANDBOX and the patch as its header (pages_ui.c
  `head_row`, 36 px), a line with the device and the page, the rows through pages_ui.c's `row_bar` (the device page's
  bar, now shared), the rail, and the device page's sand footer saying `BROWSER PLAYS · FM-1 MUTED` (or
  `TURN ON MIDI OUT: GLO, K3`) with the battery; before the first page a card. A page redraws only the rows and header that changed. K1..K4
  (`sandbox_knob`): from the position the editor sent, a choice a click (steps > 1) or 1/127 (5/127 fast), sent as CC
  16..19, the bar moving at once; the editor's next page does not take a turned knob's position back for 400 ms
  (`SB_ECHO_MS`). Only OCT, HOME, PLAY, GLO and the menu act on the FM-1 (`SB_OWN_BTNS`); every control still goes out as
  MIDI first (with MENU > MIDI OUT on). The keys play no Drum map and arm or mute nothing. PRESET waits
  (`SANDBOX: NO PRESET`). Tests: panel_test.c (mute on / off, the card, the page, the knobs, the buttons, the lapse, the page coming up),
  `tools/ui_preview.sh` with `SANDBOX=1` / `SANDBOX=2` (`MIDIOUT=0`).

## Voicing key range: channel, low, high (#57 decision 13, 2026-10-18)

- The Voice allocator has `channel` (all, 1..16), `low` and `high` (note names, C-1..G9; defaults all / C-1 / G9). A group takes a key when it lies in low..high and, for keys from the keyboard or MIDI, it comes on the allocator's channel, or with `all` on the device's channel (MENU > MIDI CHANNEL; every channel in the browser). The rule is `takesKey` (patch.ts) and `takes_key` (engine.c). The shared keyboard (Main pitch / gate / vel) and the Arpeggiators play the device's channel only. An arpeggiated allocator's range judges the Arpeggiator's notes (the arpeggiator itself takes every key of the device's channel); its channel is not used. Note offs follow the same rule, so an off on another channel does not end a note.
- Splits and layers: two allocators with low / high side by side split the keyboard; allocators on channels 2, 3 ... make the FM-1 multitimbral over MIDI. Every note-on message now reaches the engine whatever MENU > MIDI CHANNEL says (main.c `midi_drain`); the other channel messages still obey it. The panel's 27 keys play on the device's channel (1 when omni).
- An allocator with a channel or range always gets a poly group of its own (deviceView), even with one voice. Binary format 25: the group record (`GROUP_REC` / `ENG_GROUP_REC` 48 bytes) ends with u8 channel (0 = the device's), u8 low, u8 high; `ENG_PATCH_COMPAT_VERSION` 31 today (older stored patches fall back to the fallback patch). Browser: Web MIDI passes the channel (`input.ts`, worklet `on` / `off` `ch`); `Engine.channel` is the device channel (0).
- Tests: `keyrange.test.ts`; golden kit `alloc-split` (three groups: below C4 on any channel, C4 up on channel 2, channel 3; notes on channels 1..4; a mutated C channel test fails it). Not verified on a device.

## Editor link both ways (#65, 2026-10-18)

- **Live sync is the default on connect (#171).** Connecting (FM-1 & MIDI's Connect or the Connect FM-1 button at the main area's top right) runs `offerSync` (main.ts): `syncOnConnect` (device.ts, pure) gives `too-big` (the patch does not fit: no question, Live stays off), `off` (Not now was chosen in this visit: `sessionStorage['matryoshka.sync-declined']`) or `ask` (the `#sync-ask` dialog: Sync, Enter; Not now, Esc). The FM-1's patch cannot be read (SLOT_INFO gives a slot's name and length, not its data): main.ts passes no device binary, so a patch that fits always asks, and "Open the FM-1's patch" is left out. `syncOnConnect` also has a `sync` result (the FM-1's patch equals the editor's binary: on without asking) that nothing reaches until the patch can be read (#176). A reconnect with Live on sends the patch again. The FM-1 chip (`chipState`) reads FM-1 · not connected / synced / not synced / patch too big to sync, or `FM-1 · SANDBOX CONTROLLER` in sandbox mode ("Sandbox mode" above); a click while not synced offers sync, otherwise opens FM-1 & MIDI. FM-1 & MIDI has no checkbox (#180): its sync line shows the chip's state (`syncLine`, device.ts: "Synced with the FM-1 · Stop syncing", "Not synced · Sync", a sandbox patch's "Sync" into sandbox mode and its "Stop syncing", or the text alone while not connected), and its button calls the same `setLive` (the one switch; the state is `liveOn` in main.ts).
- The FM-1 tells the editor which slot it plays: SysEx SLOT_NOW (0x43: slot, name) whenever it loads a slot (PRESET, program change, boot) or SAVEs. Its K1..K4 and patch buttons reach the editor as the USB MIDI CC of the MIDI out map (MENU > MIDI OUT on). With Live on, its knob turns move the rows of the editor's page in focus (CC 16..19), or arrive as PARAM_NOW while the FM-1 plays the editor's patch ([D-457](ledger/link-and-midi.md#D-457)), without being sent back and presses its patch buttons (`Editor.pressButton`: a switch flips on the press); the status line names the slot.
- The editor's patch buttons go to the FM-1 as CC 80..86 presses / releases (a switch: one press and release); its knob turns as PARAM as before. STORE writes the running patch into the slot the FM-1 plays; "Store to an FM-1 slot…" (palette) writes the open patch into any slot (SLOT command) without switching to it; the Library's bank upload writes all 64.
- Not verified on a device: USB is not emulated.

## Device pages: the knobs follow the focus (2026-10-19, branch device-pages)

Decided with the user (design canvas https://claude.ai/artifact/R8qCCtaZ8RghG1QRYeahgV): every top-level module or assembly
of the canvas is a **device** the FM-1 plays; its card's rows are its **pages**, four rows each, and K1..K4 turn the rows
of the page in focus. Assemblies hide the inside: what the card shows is what the player gets.

- Model (`web/src/pages.ts`, tests `pages.test.ts`): `devicesOf(patch)` = Main, then each Steps track followed by the devices it drives, then the other top-level modules
  (not Part, editor-only) and assemblies with rows in Tidy's reading order (columns from the left, half a card of slack,
  then from the top), the Output last (the grouped order, [D-217](ledger/device-ui.md#D-217); "The environment's order" above). An assembly's rows are its promoted parameters; a heading (`ParamRef.head`) starts a **section** (rows
  before the first heading take the assembly's name), a section holds **groups** of at most `PAGE_ROWS` (4) rows and each
  group is one page ("Filter 1/2" = the section's first group). `groupStarts` decides them: groups fill in fours, a
  `ParamRef.group` flag (a page break set by hand in Arrange mode), a `ParamRef.pin` flag (a page start Arrange kept so a
  move did not reflow the pages around it; no ×) or a column break ends one early (the flags belong to the position like
  `col` / `head`), a display does not count and starts the next group when the last is full. Cards draw a dashed divider above a
  group that has no heading or column of its own (`.erow.gstart`). A plain module's rows are its parameters (not
  `onScreen`), four to a page (`moduleRows`, the FM-1 makes the same pages itself), labelled with the long name where it
  fits `NAME_MAX` (12).
  An envelope's display row (adsr / env `view`) puts its shape on the page holding its rows (`Page.display`).
- Main's knobs are **edit bindings**, not signals: the Main module lost the outputs and parameters k1..k6 (format 29).
  `migrateKnobs` (`knob-migrate.ts`, run by `validatePatch`) turns an old patch's knob cables into a "Macros" assembly of
  **Macro** modules (new type, `value` 0..1, one output; C: `m_const`), one per knob used, at the knob's old value and
  with its old panel label as the row label, placed top left (everything else moves a column right when that spot is
  taken), so it is the first device: the old performance page. The factory patches no longer route knobs (gen-presets.ts):
  their instruments' cards are their pages. The tutorial's knob steps teach the focus and the Macro module instead.
- Editor (editor.ts): `Editor.devices` / `focus` (`fixFocus`), the dock's K1..K4 (`boundKnob`, dials at the row's
  position in its range; choices and switches snap) and two pickers DEVICE / PAGE (`fillFocus`) in place of K5 / K6. A
  press on any row (`focusRow`, capture phase) puts its page on the knobs. The bound rows get a ring and a numbered badge
  in the knob's colour (`markFocus`, `.param.bar.bound`); while an assembly is arranged every row shows its knob and
  where its pages start (`.page-start`). Dotted lines from the dials to the rows (`positionBindings`, `svg.bind-cables`,
  over everything; a row out of view gets none). MIDI CC 16..19 turn the bound rows (`Editor.turnKnob`, from main.ts's
  sink). The knob ticks under sliders (knob-rest.ts) are gone with the knob outputs.
- **Main dock: button block (#113, design board D):** the knob column is K1..K4 with their captions, then the DEVICE / PAGE
  pickers under them; each dial's binding wire starts at a fixed `.knob-jack` on the dock's top edge (ring + core in the
  knob colour, a faint stem down to the dial; `pointer-events: none`, not a port). The button block is the FM-1's two rows
  in device order (`dock-buttons.ts` `FM1_BUTTON_ROWS`): FX SCL ENV LFO EDIT GLO / HOME SAVE ARP SEQ PLAY REC. HOME SAVE
  SEQ REC are greyed and disabled (`.panel-btn.device`), PLAY is the transport switch (`#arp-btn`, Space). The seven
  patch-button jacks (`.dock-button-jacks`) share the grid's columns plus a 12 px lane right of REC for ARP's jack
  (`jackColumn`); gold traces (`svg.button-traces`, `Editor.positionTraces` from `positionCables`, `tracePath`) run
  straight up from the top row, and from ARP up into the gap between the rows, right past REC and up the lane.
- Knob colours are the logo's (style.css `--k1..--k6`: coral, gold, teal / seafoam, sand, lilac, blue), every mark with
  its number. Cables are drawn by the **role of the input** they land on (`cable-role.ts`): into a signal input the
  accent, bold (`role-signal`); into a CV input, a pin or a thumb, and into `pm` / `side`, the secondary colour, lighter
  (`role-mod`); into a gate / trigger / clock input a hollow rail in the gate colour (`role-gate`); into a keys input a
  three-wire ribbon in the ink colour (`role-keys`). The rail's core and the ribbon's core and centre wire are extra
  paths over the cable (`.cable-core`, `.cable-wire`, `pointer-events: none`), made in `Editor.drawCables` for the
  cable and its dock and card-entry copies, positioned with it. A route the user made inside a card (a side input to a
  parameter, `.cable.alias`) is solid too; a module's built-in link (`.cable.alias.fixed`) stays dashed and muted.
  **The rule (#156): solid = you made it (saved in the patch, has undo); dashed = the app is showing you something** (a
  knob target, the armed track, a cable mid-drag, a built-in link). Dashed lines march toward the receiving end
  (`@keyframes cable-march`, one dash period per cycle, off with `prefers-reduced-motion`). Assembly members get a
  tinted border, not a dashed one.
- Binary format 29 (`patchbin.ts`): header flag bit 5 = a device pages section after the step values, before the macro
  ranges (which stay last: proto.c edits them in place). Per device a kind byte: 0 = a plain module (its index; the
  FM-1 makes its pages from defs.h), 1 = an assembly with its name, pages (name, part, parts, envelope module + 1, row
  count) and rows (module index, parameter index, label), texts length-prefixed. A Voice allocator's rows (voices,
  assign, legato, priority, unison, steal) name its group setting: in the device form the allocator is its group's Part, and
  the parameter byte is 0x80 + the field (`POLY_ROW_PARAMS`). `binaryPage` / `editorPage` map the editor's focus to the
  binary's indices. `eng_devices_end` (engine.h) walks the section; `eng_load` skips it.
- Page row extras (format 35, #357, #358): bit 6 of a row's parameter byte (`ROW_MORE`, engine.h `ENG_ROW_MORE`; never on
  a poly row) says the row's extras follow its label: u8 n and n (module index, parameter index) pairs, the further
  parameters the row sets, then u8 k and k texts, its positions' names in capitals. A row without them is written as
  before, so every binary written before them is unchanged. The FM-1 keeps where each row's extras start (`ppage_t.xo`,
  an offset into the running binary): K1..K4 and MIDI CC 16..19 write the row's value to each further parameter too
  (`pages_also`, after the first; PARAM_NOW names only the first, the editor sets the rest), a preset loaded on the FM-1
  does the same (`dp_load`, `dev_row_more`), and a named position shows its name for the value (`row_name`). A Selector
  module's `pos` row spans 1..count on the FM-1 (`row_top`: the knobs, CC, the bar and MIDI out), as on the card.
- Protocol: FOCUS 0x29 (host → device: show a page), PARAM_NOW 0x47 (a row turned on the FM-1: module, parameter, Q16)
  and FOCUS_NOW 0x48 (the page the FM-1 shows) from the device; INFO feature bit 4. With Live on the editor follows the
  FM-1's page and turns, and sends its own focus; an upload is followed by the focus.
- Firmware (`firmware/src/pages_ui.c`): the device page is page 0. The layout is michael glaviano's design of 2026-10-24
  ([D-234](ledger/device-ui.md#D-234)); every number of it is one of the `LK_*` constants at the top of the drawing code
  (point depth 18, header 36, footer 15, tab at 2, header strength 15 %, edge 2, stack gap and inset 3, value 26 px,
  the toast 60 / 6 / 32 / -5 / 6 / 1 / 5), and the type sizes are fonts of their own (`tools/gen_font.py`: `FONT_F` 14,
  `FONT_H` 16, `FONT_N` 20, `FONT_V` 26, `FONT_T` 32, capitals, digits and signs; a check in pages_ui.c fails the build
  when a constant and its font disagree). Text sits as the mock's canvas puts it: a text's middle at the mock's y, its
  baseline a third of its size below (`BASE6`).
  - The header (y 0..35, `head_row`, a scanline at a time): three sections, the device | its page group | the group's
    pages, widths 2 : 3 : 1 of the screen. A section whose name needs more (its width + 14, + the point for the second;
    the third 12 + the point) grows and the others give the rest up evenly, never below their own need; two names too
    long for the screen together are cut, the longer first (`head_layout`). The first two sections end in a point 18 px

  - The bars (y 40..220, `bar_row`): four equal bars 4 px apart in the area between the header and the footer (4 px from

    the parameter (rows 4..h-4); an accent tab in the hue, 4 px wide, 45 % of the bar high, 2 px from its left; the name
    10 px after it, the value right, 6 px from the bar's end, its unit after it in mist (`FONT_F`). A row the page lacks

  - The footer (y 225..239, sand, `foot_row`): the patch's name (ARM / REC and the track's name while one is armed, red

### LFO shape

The LFO shape input uses the block average in 0..1 to set its triangle rise time and pulse width. Without a cable it uses 0.5. At the ends its triangle becomes a falling or rising saw. Its appended `pulse` output shares the phase, reset, sync and depth of the main output. Both outputs reverse with `dir`. Sallen 20 exposes this as the modulation generator's continuous WAVEFORM control ([D-436](ledger/modules.md#D-436), Proposed).
