# Tutorial design

The course has twelve numbered chapters plus the tour (below). Each teaches a synthesis idea through a playable patch and a practical editor technique. This document records the QA revisions requested on 2026-10-14; implementation tickets are [#23–#35](https://github.com/glvno/matryoshka/issues?q=is%3Aissue+label%3Aready-for-agent).

## Panel size

The docked panel grows up from its corner and scrolls once it reaches the top margin (CSS). A panel placed by its top edge (Follow, a drag, the middle of the screen) does the same: `Tutorial.fit`, run by a `ResizeObserver` on the panel, after every placement and on window resize, moves it up as its content grows until it reaches the top margin, and caps its height at the window minus the margins, so a long step scrolls instead of running off the screen.

## The offer

Every visit to the Patch tab (not one opened from a share link) shows a centred card offering the tutorial: **Start the tutorial** (the first published chapter) or, with progress in a published chapter, **Resume**; **I know what I'm doing, just show me around** starts the tour (below); **Not now** or Escape closes it for this visit. Ticking **Don't show this again** stores `matryoshka.tutorial-offer-off` in localStorage and reveals a note saying where the tutorial lives (**Tutorial ↗** in the sidebar, or **☰ Workspace → Tutorial ↗** below 700 px, where the sidebar is folded away) while that button pulses; unticking undoes both. `Tutorial.welcome()` in `tutorial.ts`.

## Progress and recovery

The course is data: `web/src/tutorial/course.json`, written by the lesson editor and compiled by `chapters.ts` (shape in `course-schema.ts`, part semantics in `parts.ts`, code-only checks and roles in `registry.ts`). A **task** step's requirements (parts) are checkboxes in its own text; when they are met it waits for **Continue**, unless it is marked **Move on by itself** (`advance: true`), which advances 900 ms after they are met. No step of the course advances by itself at the moment. A **Continue** step has no requirements: it breaks up text or is a listening break (optionally with the playback buttons and a pointer at a module, jack, slider or sidebar control). Creative comparisons are ungraded; their text distinguishes optional settings from the settings needed for the next exercise. Frame resizing is explicitly optional.

There is no "do it for me". **Back** restarts the previous step from the patch the learner had when entering it (kept in memory per step of the chapter; after a reload, the canned beginning state); the current patch is kept as a variation first. **Start step over** does the same for the current step without keeping a variation: it is one editor change, so Undo brings the discarded work back.

A later matching state never makes a preparatory step moot: a newly grouped, collapsed assembly is not evidence that the learner expanded it. Structural prerequisites that are still relevant must hold before advancing or finishing; when one no longer holds the panel says so (put it back, or go Back). `superseded` marks work deliberately replaced later. A step is transient (skipped when judging whether a finished patch completes a chapter) when it is a Continue step or any requirement is momentary: an event, a slider "moved from its start", a resize, a save, or a custom check marked momentary.

**Requirements in the text.** Every requirement has a permanent `id`, made once from what it checks (`partSlug` in parts.ts: `osc-out-vca-in`, `unplug-main-gate-vca-cv`, `adsr-a`, `add-osc-2`, `my-voice-collapsed`; `-2` when the step already has it). The instructions place it as a link around the words that ask for it: `[Drag the LFO’s out to the Filter’s cv jack.](req:lfo-out-filter-cv)`, several ids comma-separated when one phrase asks for more (`req:a,b`, ticked when all hold); it works in headings, list items and sentences (`markdown.ts` turns the link into a checkbox; `placedRequirements` lists them). The panel ticks a box while its requirements are met and unticks it when they stop being met (momentary ones stay ticked once they happen in the step); the boxes are display-only. The controls of the first unticked box in reading order are highlighted (the box gets the class `next`, unstyled); clicking a box points the highlight at that box's controls instead while it is unticked. A guard the learner does not act on (silence without a key, an old cable already gone) is `hidden: true` and not shown. The validator requires every requirement to be placed or hidden, rejects ids the step does not have, and allows `req:` links only in a task step's instructions (not in Why, a Continue step, the introduction, payoff or challenge). There is no separate checklist. Close cancels pending advances and audition; Resume restarts polling. The saved page and stable step ID survive reload, with a fresh entry snapshot for delta-based checks.

Every chapter loads a prepared starting patch. Before replacing the open patch, the runtime stores an immutable variation in `matryoshka.tutorial.variations`, including patches whose names begin with Tutorial. This archive is independent of the FM-1 bank. It never evicts or replaces a different same-named version. A storage failure is shown and leaves the open patch in place. Named sketches can also be saved during any exercise or at chapter completion. **Tutorial → Your saved variations → Restore** first keeps the current patch, then restores the selected copy.

Assembly saves go to the real library. Helper saves retain a changed prior instrument under a unique “previous” name and leave one active tutorial tag; failed storage writes are reported. A fresh save check compares the definition actually saved during the step with the current assembly, including its modules, cables and exposed controls; saving an unrelated assembly does not count. Later chapters use the learner's tagged or named instrument when available, otherwise the bundled version: the definition stored with the reference patch of the step that saves it.

Every task step stores a **reference patch**, the patch after doing it. A step's beginning state is the previous task step's reference (or the chapter's start: a new patch, an empty canvas with no modules at all, the previous chapter's end, a factory patch, or a stored patch); a chapter's end, its intro preview and its Examples entry are its last reference.

## Listening and panel behavior

Every exercise and chapter finish has Note, which holds C4 (no Chord: patches are mono unless a poly assembly says otherwise, so a chord button would sound as one note; steps that need a chord ask for one held on the keyboard), and no Riff button: a looped riff rarely fits the tutorial patch's sound ([D-663](ledger/tutorial.md#D-663)). The intro's preview holds the same note. Note is a toggle; **Release notes** lets tails decay, while **Stop** silences playback, including autonomous patches. Moving between steps (advancing, Begin, Back, Start step over) leaves the sound alone: a held note keeps sounding and the output stays on. Choosing a chapter, the chapter menu, Close, leaving the window, Stop and Panic cancel tutorial notes and timers and mute the output. **Begin** turns the output back on (and starts audio if the browser had not yet), so chapter 1 needs no Enable audio step and its first drone is heard. A cancelled audio startup cannot restart playback afterward.

An intro's **Preview the finished sound** sends the completed patch to the audio engine for eight seconds without changing the editor patch, layout, history, selection, snapshots or library. Normal preview completion restores the editor sound and previous transport/mute state. Explicit Stop, blur and close silence it. Audio starts from a playback click.

The panel docks at bottom right by default. **Follow** optionally places it near the highlighted target and scrolls that target into view. Drag the handle, or use its arrow keys to move it; Home docks it again. Below 650 px it docks immediately at the bottom, clears desktop inline positions and scrolls internally. The highlight on what to do next (gone once the task step's requirements are met; a Continue step's pointer stays) is a steady 3 px outline plus a ring that grows out of it and fades every 1.2 s (`tour-ping` in style.css), wide enough to catch in peripheral vision while reading. Reduced-motion preferences suppress movement and pulsing (the highlight becomes a still halo). Required controls, then the optional Why, then expected listening outcomes keep the lesson readable.

## The tour

A chapter with `tour: true` (the lesson editor's **Tour** check box; at most one, and it cannot continue from or into another chapter) is not numbered: `LISTED` leaves it out, `TOUR` (chapters.ts) points at it, the offer card's third button starts it, the tutorial menu lists it first with an arrow, and its panel says "Tour" instead of "Chapter n of m". Its end offers chapter 1. It is the last entry of `course.json` so the chapter indices do not move.

The tour ("Overview for advanced users") is for people who already patch. It starts from a stored patch (the former factory Warm Pad: stack voice and echo, kept in course.json since the factory patches were replaced on 2026-10-18) and stops at what is different here: assemblies (expand stack voice), slider thumbs as jacks (LFO onto the filter's `res`, with the base and knob ticks), the Main panel (morph; the arpeggiator is a module added with ARP, and polyphony lives on assemblies), the command palette (add a Wavetable), a list of the notable modules, and the listening tools (scope, bypass, changes, share links).

## Chapter payoffs

| Chapter | Build and audible payoff |
| --- | --- |
| 1. How to make a noise | From an empty canvas: a new patch, then an oscillator on Main's pitch straight into the Output (an endless drone). Unplugging it (the fourth step) is the only way to stop it, so a VCA goes in between: silent until Main's gate opens its cv (the sixth step). Then a Scope shows the wave, and holding a note while moving the wave slider compares the shapes. |
| 2. Shaping sound with envelopes | Swelling attack/release versus a fast, zero-sustain pluck; the held pluck really dies. |
| 3. Subtractive voice | Separate cutoff and resonance listening; keyboard tracking, slow wah versus rhythmic wobble, then knob routing and live/base values. |
| 4. Your first assembly | Fold five modules into one instrument, expand explicitly, promote two controls, optionally resize, then save the current instrument. |
| 5. An effect assembly | Insert and audition Delay, Reverb and Chorus separately before grouping. Compare dry, small room and large space. |
| 6. Second instrument: FM | Hear the gated carrier before modulation. Manually duplicated oscillators need a new pitch cable; helper repairs partial work. Compare mellow/hollow/metallic ratios, then envelope and nested space. |
| 7. Plucked and struck | Hear the string and modal body before adding noise through a comb. Compare muted/ringing chords and breathy tone; save Pluck. |
| 8. Wavetables and grains | Hear a gated dry vowel first; keep an output through every insert. Capture a four-note chord, freeze it, explore pitch/spray and return to live input. |
| 9. Two instruments, one keyboard | Solo and blend layers. Map a full-depth knob to 150–4000 Hz. Save the patch as a variation, change a few sliders, then choose the saved variation as a compatible morph target and move Main morph. |
| 10. A random melody machine | Listen to chance before writing a reply. Sequence changes and instrument gates share the musical subdivision; a second divider derives every-other-note FM triggers after 24-ppqn conversion. Divider outputs retain input pulse width. |
| 11. Drums from noise | Noise through a high pass and a very short envelope becomes a hat (saved as Hat); a held hat dies with the documented levels/rates. Kick and snare come from the library, a clock and divider make the pattern, a loose mixer outside factory drums mixes the kit, then the backbeat and an eight-bar miniature using the saved Pluck, shared as a link. |
| 12. Voicing | A poly assembly fed by a Voicing module (a stored starting patch): mono and legato, retrigger, which key wins, portamento (only when legato, longer for bigger jumps), unison with blend and stack, several notes, then drift, tolerances and flaws by hand. |

Each finish names a specific accomplishment, offers an optional creative challenge, and lets the learner name a variation. Chapter 11's eight-bar miniature is an ordinary shareable patch within the FM-1's 64-module limit: two bars of beat, four with melody, an open-hat flourish on bar seven, then a return. A divider and slow sequencer store the form; no browser timer is needed. The arrangement reuses the kick sequence for melody and drives hats with the eighth-note clock. Engine sequencers advance on the first edge, so the first sounding slot is s2, then s3…s8, s1. The pattern builder accounts for that phase explicitly.

## QA boundaries

Course tests run the validator over `course.json`, check every step's requirements and highlight on its beginning state and its reference, render sound from every chapter's end, and test capture against the course's own reference patches. Regressions cover manual duplication, nested factory mixers, held-note envelope tails, audible intermediate patches, real morph targets and macro units, the clock hierarchy, stale library saves, the actual eight-bar control sequence, audition cancellation and immutable variation storage/failure.

Browser checks exercise close/resume, reload at a delta-based step, assembly expansion, deliberate Continue, playback controls, preview, saved variations and desktop/mobile docking. Browser audio lifecycle is separate from DSP tests; neither is a claim of firmware or device validation. The existing development server on port 5173 is used; do not start a second server.

## Fixed links

Dedicated parameter inputs remain permanently linked (`ParamDef.input`). Their routes are grey and inert; user-made routes remain editable. This tutorial revision changes browser behavior and course patches, not the firmware patch format or DSP definitions.

## Writing lessons locally

Run the usual `cd web && npm run dev`, then choose **Edit lessons** at the bottom of the synth sidebar, or open <http://localhost:5173/lesson-editor>. The existing server on 5173 serves the editor; no separate process is needed. Keep the synth open in another tab of the same server: the editor links to it.

**Structure.** The course browser lists chapters and their steps; drag to reorder (steps within their chapter), or use ↑ / ↓. A chapter page edits its title, patch name, start (new patch with a voice count, an empty canvas, previous chapter's end, factory patch, or the synth's current patch stored), introduction, payoff and challenge, and adds steps at its start. A step page adds a task or Continue step after it, duplicates or deletes it. Ids are made from the title once and never change; learners' progress follows them.

**Publishing.** A chapter page has a **Published** check box (`unpublished: true` in `course.json`, right after the title; absent = published). The built site offers only published chapters: the chapter menu, the Examples picker, "Chapter n of N" and the next-chapter button count and number them alone, and saved progress in a chapter that is no longer offered falls back to the menu. The dev server lists every chapter, marked UNPUBLISHED, so it can be played before it ships. New chapters start unpublished. An unpublished chapter's data is still in the bundle (a `continue` start can depend on it); publishing hides it, it does not remove it. Only chapter 1 is published at the moment.

**Requirements.** A task step is a list of parts, built from module definitions: module present, cable, cable removed, slider (≤ ≥ = ≠ between, or moved from its start, in the parameter's units), routed to a parameter (a thumb drop), pin map, attenuverter, macro range, assembly (exists, expanded, collapsed, promoted slider, exposed output, merged inputs, contains, resized, saved), poly (a poly assembly's parts, assign, legato, priority or unit), event (notes, undo, zoom, probe, selection, bypass…), sound (sounds with a key held / silent without a key, rendered offline) and custom checks from `registry.ts`. Parts name modules by shape, never by id: the n-th of a type (or every one, or the one outside assemblies), a module role, or a type inside an assembly role. Each part writes its own checklist line; an optional override replaces it. **Roles** (a page of its own) name assemblies by the types they contain or their library name, and modules inside them; code roles (carrier, modulator, keys: Main or any Part module, so a pitch / gate requirement still holds after the modules went into a poly assembly) live in `registry.ts`.

**The synth link.** With the synth open, every requirement shows ✓ / ✗ against the synth's patch and the preview's checkboxes tick against it. Each requirement row shows its id and whether the instructions place it (✓ placed, ⚠ not in the text, hidden), a **hidden** toggle and **Insert in text**, which wraps the selected instruction (a heading, list or number marker stays outside) or inserts the generated line at the cursor; the preview lists requirements the text does not place yet. **Try this step in the synth** loads the step's beginning state. **Record in the synth** loads it, the author does the step, **Stop recording** lists what changed (modules, cables added and removed, sliders as at least / at most the new value, routes, assembly changes, events) to tick into requirements, and keeps the result as the step's reference patch (and an assembly saved meanwhile as the bundled copy). Re-recording a step with recorded steps after it says so; Course checks shows any that no longer hold. The link is a `BroadcastChannel` between same-origin tabs (`link.ts`), development only.

**Riffs.** A step may still carry a `riff` (a loop of notes once read from a MIDI file for the removed Riff button): the course loader checks its shape (`riffProblem` in `web/src/tutorial/riff.ts`) and Save keeps it on one line, but the lesson editor has no control for it and nothing plays it.

**Course checks** run on every change (`validate.ts`): every part names types, ports, parameters, roles and checks that exist; every reference patch passes its own step (momentary parts aside) and every earlier structural step of its chapter; a saving step stores its definition; each chapter's end completes it; required text is not empty. Errors block **Save all changes** (Cmd/Ctrl+S), which writes `web/src/tutorial/course.json` (reference patches one per line); a task step without a reference is a warning, a step that a later one undoes without being marked superseded a hint. The local synth reloads after a save, while the editor keeps its position. Saving does not commit or publish anything.

Every prose field supports Markdown; titles remain plain text. Open **Markdown formatting guide** above the fields for examples. Markdown supports **bold**, *italics*, strikethrough, inline code, links, headings, bullet and numbered lists, quotations, fenced code blocks, tables, images, footnotes, and horizontal rules. Blank lines separate paragraphs; single newlines remain visible line breaks. Prose headings appear below the lesson title in the document hierarchy. Web links open in a new tab so they leave the learner's patch open. Raw HTML is displayed literally; executable URL schemes are rejected. `web/src/tutorial/markdown.ts` provides the same parser, DOM wrapper and challenge layout to the runtime and preview, with shared `.tutorial-prose` styles. Wide tables and code blocks scroll inside the card, and images fit its width.

Footnotes use `A detail.[^note]` with `[^note]: The explanation.` below, or an inline note such as `A detail.^[The explanation.]`. Put the reference and definition in the same field; each field numbers its own notes. Indent additional paragraphs by four spaces. Notes can contain ordinary Markdown. Clicking a note number scrolls to its explanation; each return arrow goes back to its reference, including repeated references. Navigation keeps the current patch URL and stays in the lesson. Generated IDs are unique across fields, so Instructions and Why can both use `[^1]`.

Drafts are kept in browser storage as you type. Each tab retains its own draft across reloads; the most recently edited draft is also available when reopening the editor. **Download draft** exports a recovery copy. **Reload saved course…** explicitly discards the current draft after an inline confirmation. If the file changed outside this editor or another tab saved first, saving is refused: download your draft, reload the saved course, then reconcile your edits. Storage failures remain visible; keep a download before closing if recovery is unavailable.

The GUI is served only by the Vite development server. Its fixed-path JSON save endpoint accepts local, same-origin requests, checks the course's shape (`validateShape`) and the source revision, and writes atomically. Neither the GUI, sidebar link nor save endpoint is included in the production site or Vite preview server.
